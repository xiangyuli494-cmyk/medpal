## 0 一页纸结论

**一句话**：选医疗行业里最窄的一条链路——「门诊主诉 → 跨文档取证 → 科室与检查建议」，把赛题的四条要求各做成一件可验收的东西，用 **1 个自研 MCP 服务 + 3 个 Nexent Skill 包 + 1 个主智能体** 承载，四周交出可运行 Demo、可复现评测、可开源仓库。

**三条硬决策**

| 决策 | 内容 | 理由 |
| --- | --- | --- |
| 砍硬件 | 赛题不要求终端设备。算力 = 本机 Docker 跑 Nexent + 云上模型 API。唯一门槛是装 Docker Desktop + WSL2 | 已有的陪诊终端项目周期太长，且不在赛题评分项里 |
| 砍行业 | 只做医疗，只做「主诉 → 建议」一条链路。金融、制造、政务不碰 | 小而精；评委看的是机制是否成立，不是行业数量 |
| 复用存量 | 本体冷启动用 **ICD-10 编码表（约 2.6 万条）+ 卫健委临床路径（15 份）+ 药品说明书（20 份）**；回归网用仓库里**已通过的 65 个单测**。OpenCMKG 只作「若拿到可再分发许可」的加速项 | 这三类都是现在就能下载、能开源的资产；回归网已验证存在。不把 W1 进度押在未落地、且许可受限的数据集上 |

**四个交付物（对应赛题四条要求）**

| 赛题要求 | 我们的交付物 | 怎么验 |
| --- | --- | --- |
| 多模态异构数据统一识别、理解、资产标识 | 资产登记服务 Asset Card + 文本/表格/图文三类各 ≥20 份样本入库 | 打开资产台账，每份文件都能看到模态、来源、版本、敏感级、可引用锚点 |
| 低资源本体半自动化构建、持续更新、与行业标准对齐 | 本体进化流水线（抽取→校验→对齐→发布）+ 本体 v1.0 快照 + v0.9→v1.0 差分报告 | 一条命令产出差分，人工确认后版本 +1，旧版本可回滚 |
| 深度集成 MCP 与 Skills 编排，检索-推理双驱动 | 自研 MCP Server（10 个工具，核心 7 + 辅助 3）+ 3 个 Skill 包 | 在 Nexent 控制台能看到工具清单，S1/S2/S3 三个技能都能跑通 |
| 跨文档多跳推理、决策链可溯源、Skill 模板可复用 | Trace 数据结构 + 决策链报告 + 模板导出命令 | 任取一条问答，每一步都挂得住证据锚点（文件#页/表行/图区） |

**最大风险**：本机没有 Docker、没有 WSL。这是唯一会卡死全组的点：W1 第一天（10/26）就装，**10/28（周三）24:00 仍起不来即切云**，见第 12 章。

**已经跑起来的部分（截至 2026-10-22）**：`agent/` 里有一套可运行的骨架——MCP Server 10 个工具（核心 7 + 辅助 3）、SQLite 本体 v0.9（17 条三元组 + 1 份资产 + 15 个锚点）、3 个 Skill 包、14 条评测集、三套测试全绿（stdio / streamable-http 两种接入方式都验过）。缺的只有 Nexent 本体（要 Docker）和真实规模的样本与三元组。所以 W1 的任务不是「从零搭」，是「装 Docker + 喂数据 + 换掉 SQLite 里的种子」。

## 1 赛题拆解：把四条要求翻译成四件东西

赛题原文的四条要求，落到工程上其实是四个模块加一条数据流。先把「要求 → 模块 → 产物 → 验收人」对齐，后面所有排期都从这张表推。

| # | 要求原文关键词 | 对应模块 | 产物 | 验收人 |
| --- | --- | --- | --- | --- |
| R1 | 多模态异构数据资产的统一识别、理解与资产标识 | 数据资产层 | Asset Card 台账 + 解析器插件 | T5 |
| R2 | 低资源本体半自动构建、动态更新、与行业标准对齐 | 本体层 | 本体快照 v0/v1 + 差分报告 + 对齐表 | T4 |
| R3 | 深度集成 Nexent 的 MCP 协议与 Skills 编排 | 工具层 + 编排层 | MCP Server + Skill 包 | T1 |
| R4 | 跨文档多跳、决策链路可溯源、Skill 工作流模板 | 执行层 + 输出层 | Trace + 决策链报告 + 模板导出 | T2 |

再加一条隐形的 R5：**智能体基于 Nexent 平台可运行**。这条不是模块，是约束——所有自研能力必须通过 Nexent 认识的接口暴露（MCP 工具、技能包、北向 API），不能自己另起一套前端把 Nexent 绕过去。评委大概率会现场点开控制台看。

### 1.1 「可进化」到底指什么

赛题标题里的「可进化」最容易被讲成空话。我们的定义是三条可观测的行为：

1. **本体会长**：新文档进来后，系统能提出候选三元组（新增/修正/废弃），人工确认后本体版本 +1，旧版本可 diff、可回滚。
2. **决策会变**：本体从 v0 升到 v1 后，同一批评测题的回答会变化，且变化方向可解释（新证据命中、旧结论被推翻）。
3. **能力会沉**：一次成功的执行能被导出成 Skill 模板，下次同类问题少走几步。

演示时必须把这三条都演出来，其中第 2 条是加分点——大部分队伍只会演「知识库变大了」，不会演「决策因此变了」。

## 2 场景：为什么是医疗，为什么只切一刀

### 2.1 候选对比

| 行业 | 数据可得性 | 标准体系是否现成 | 我们已有资产 | 判断 |
| --- | --- | --- | --- | --- |
| 医疗 | 高（ICD-10 编码表、临床路径、药品说明书全公开） | 强（ICD-10、卫健委临床路径、诊疗指南） | ICD-10 编码表 + 15 份临床路径 + 65 个已通过单测 | **选它** |
| 政务 | 高（政策文件公开） | 中（有公文格式规范，缺可机读本体标准） | 无 | 备选 |
| 金融 | 低（行情与产品数据多为商业授权） | 中 | 无 | 放弃 |
| 制造 | 低（设备数据在厂内） | 弱 | 无 | 放弃 |

医疗是唯一同时满足「数据公开」「标准现成」「我们已有积累」三条的行业。R2 里「与行业规范、标准体系对齐」这一项，医疗有 ICD-10 和临床路径可以直接挂，别的行业很难在一个月内找到同等颗粒度的标准。

### 2.2 场景边界：只做主诉到建议

**做**

- 输入：一段自由文本主诉（可附带一张检验报告图片、一张门诊记录表格）
- 过程：实体识别 → 本体多跳 → 跨文档取证（指南 / 说明书 / 临床路径 / 检验参考区间）→ 冲突检测
- 输出：建议科室（含置信度）+ 建议检查项（含理由）+ 每条结论的证据锚点 + 完整决策链

**不做**（写进 README，评审时主动说明边界）

- 不做诊断结论，不出处方剂量，不替代医生
- 不做影像 AI（CT/X 光判读），图片模态只处理检验报告单、病历首页这类版式文档
- 不做多轮长对话随访，只做单次问答 + 追问一次
- 不做真实医院系统对接（HIS/EMR），全部用脱敏样本与合成数据

### 2.3 一个具体例子（全组共用这个例子做测试）

> 主诉：反复上腹隐痛 3 个月，夜间加重，进食后缓解，近两周服用布洛芬止痛。

期望的决策链（每一步都标明「谁提供证据」，避免把推理责任错挂到编码表上）：

| 步 | 动作 | 证据来源 | 说明 |
| --- | --- | --- | --- |
| 1 | 「上腹隐痛」归一为 **R10.1**（上腹部痛） | ICD-10 编码表 | ICD-10 **只做实体归一**，不做推理——编码表里没有「R10.1 → 某病种」的鉴别边 |
| 2 | 反向查 `has_symptom`，得到候选病种 **K27 消化性溃疡** | 卫健委临床路径 / 诊疗指南 | 「上腹痛需除外消化性溃疡」这条关系来自指南正文，provenance 指向指南页码，不是指向编码表 |
| 3 | 临床路径要求 **幽门螺杆菌检测、胃镜检查** | 临床路径 | 检查项挂在 K27 节点上，与第 2 步分开取证 |
| 4 | 布洛芬说明书：**NSAIDs 可致胃黏膜损伤**，与 K27 冲突 | 药品说明书 | 冲突检测命中，置信度下调 |
| 5 | 输出：消化内科（置信度 0.7x）；建议检查：Hp 呼气试验、胃镜；建议停用 NSAIDs，胃黏膜保护剂需医师评估 | 汇总 | 每条结论必须挂 anchor_id |

这条链路跨 **4 类文档**（ICD 编码表、临床路径、药品说明书、检验参考区间）、**3 跳以上**，正好压住 R4 的全部关键词。

**必须守住的口径**：ICD-10 是**分类编码表**，只提供「症状 / 诊断 → 编码」的归一映射；「上腹痛要除外消化性溃疡」属于**临床知识**，只能从临床路径与诊疗指南抽取。把第 2 步挂到 ICD-10 上是错的，评审只要有一位临床背景的人就会当场问穿。三类证据的分工在 5.1 节的 `source_type` 里固化。

全组所有 Demo、评测题、录屏都围绕这个例子展开，避免各人各讲一套。

### 3.2 为什么这样切

**为什么自研 MCP Server 而不是写进 Skill 脚本**
Nexent 的技能脚本跑在 Docker 沙箱里，能力受限（具体版本号与限制项待 W0 在控制台核实，见 §10.0 第 1 项，T6 / 10/25），且脚本不适合做有状态查询。把本体查询、版本快照、trace 写入这些有状态逻辑放到独立的 MCP 服务里，技能侧只负责编排和话术。这样职责清楚，也方便单测——MCP 工具可以脱离 Nexent 直接 pytest。

**为什么存储用 SQLite 不用 Neo4j**
第一批 3000–10000 条三元组、两跳以内查询，SQLite 的邻接表完全够，还省一个容器。Neo4j 要多占 2G 内存、多一个部署环节，对四周项目是纯负担。方案里留了接口抽象，真要换图库只改一个 store 实现。

**为什么依赖 Nexent 自带知识库做向量检索**
自己在本地搭一套向量库要多写 500 行、多调 3 个参数、多一类故障。Nexent 的 knowledge base 支持多模态向量（平台内文档写作 `multi_embedding`；**拼写与开关位置尚未在控制台确认，已登记风险 R-01**，默认值按 `multi_embedding` 执行，W1 周一按 §10.0 规则确认或改口），正好覆盖 R1 的图文模态。自研只做「怎么用」，不做「怎么存」。

**为什么 Skill 只有三个**
技能包多了维护不动。三个技能分别对应赛题三个环节（资产、本体、决策），每个都能单独演示，合起来是一条完整流水线。

### 3.3 与 Nexent 的接触面（评审会问）

| 接触点 | Nexent 能力 | 我们怎么用 |
| --- | --- | --- |
| 智能体 | 智能体开发页 / SmolAgents 内核 | 建 1 个主智能体，挂 7 个核心 MCP 工具 + 3 个技能（辅助 3 个按需挂） |

## 4 数据资产层（R1）

### 4.1 Asset Card：资产标识的落地形式

「资产标识」不能只是给文件起个名。我们的定义是：每份数据源都有一张卡片，字段固定，能被检索、能被引用、能被版本追踪。

~~~json
{
  "asset_id": "AST-2026-000137",
  "title": "消化性溃疡临床路径（2023 版）",
  "modality": "pdf_text",
  "source": {"type": "public_standard", "publisher": "国家卫生健康委", "url": "..."},
  "version": {"value": "2023", "captured_at": "2026-10-28", "supersedes": null},
  "sensitivity": "public",
  "structure": {"pages": 12, "tables": 3, "figures": 1, "sections": ["诊断依据","检查项目","治疗方案"]},
  "anchors": [
    {"anchor_id": "AST-2026-000137#p3.t1.r2", "kind": "table_row", "text": "幽门螺杆菌检测 必查"},
    {"anchor_id": "AST-2026-000137#p5.s2", "kind": "section", "text": "胃镜检查适应症..."}
  ],
  "entities": ["K27", "幽门螺杆菌", "胃镜"],
  "kb": {"base": "med-text", "doc_id": "doc_8f21", "status": "ready"},
  "ingested_by": "T2", "created_at": "2026-10-28T10:12:00+08:00"
}
~~~

关键字段是 `anchors`。**所有下游引用都只认 anchor_id，不认文件名**。这样决策链里的每条证据都能点回原文的具体位置，R4 的「可溯源」才有落点。

### 4.2 三类模态怎么处理

| 模态 | 样本 | 解析方式 | 落到哪 |
| --- | --- | --- | --- |
| 文本 | 临床路径 PDF、指南摘要 MD、药品说明书 TXT | PyMuPDF 抽文本 + 按标题切节 | Nexent 文本知识库 |
| 表格 | 检验项目参考区间 XLSX、门诊记录 CSV | pandas 读取 → 每行转一条结构化记录 + 回写表格快照 | 结构化表（SQLite）+ 知识库文本化副本 |
| 图文 | 检验报告单扫描件 PNG、病历首页照片 | 调用平台自带 VLM 技能做版面理解（工具名以平台工具清单为准；**尚未确认，已登记风险 R-02**，默认值按 `analyze_image` 执行，W1 周一按 §10.0 规则确认或改口），输出字段 → 关键区域裁切存 MinIO | multi_embedding 图文知识库 + 结构化字段 |

图文这一类的做法要说清楚：我们**不训练 OCR 模型**，用平台自带的 VLM 技能把图片读成结构化字段，再把「字段 + 原图裁切」一起入库。这样 R1 的「图文统一理解」有了实现路径，也不需要 GPU。

### 4.3 数据来源清单（全部公开可开源）

| 类型 | 来源 | 数量 | 用途 |
| --- | --- | --- | --- |
| 疾病编码 | 中文 ICD-10 编码表（公开版） | 约 2.6 万条 | 本体主干节点 |
| 临床路径 | 卫健委已发布临床路径（公开 PDF） | 抽 15 份 | 检查项、治疗流程 |
| 药品说明书 | NMPA 公开说明书 | 抽 20 份 | 禁忌、相互作用 |

| 门诊记录 | 自行编写脱敏样本（CSV） | 20 份 | 表格模态样本 |
| 合成病历 | 自行编写脱敏样本 | 30 份 | 图文模态 + 演示 |
| 本体种子 | 由上面三类材料抽取（ICD-10 / 临床路径 / 说明书） | 首批 3000–10000 条 | 冷启动 |

**合规口径**：只用公开标准与合成数据，不接触任何真实患者数据；仓库里所有样本标注 `synthetic` 或 `public`。这条要写进 README 和 PPT 第一页——评审对医疗数据合规敏感。

### 4.4 解析器插件接口

~~~python
# parsers/base.py
class Parser(Protocol):
    modality: str                      # text | pdf | table | image
    def accept(self, path: Path) -> bool: ...
    def parse(self, path: Path) -> ParsedDoc: ...   # 返回 blocks + anchors
~~~

`ParsedDoc` 固定包含 `blocks`（带类型与坐标）、`anchors`（可引用单元）、`metadata`。新增模态只要加一个 Parser 实现并注册，不动主流程。这是给 R1 的「统一识别」留的扩展点，答辩时可以现场加一种模态演示。

## 5 本体层（R2）

### 5.1 本体 schema（先定死，别边写边改）

实体 6 类：`Disease`、`Symptom`、`Exam`（检查）、`Drug`、`Finding`（检验结果）、`Department`。
关系 8 类：`has_symptom`、`diagnosed_by`、`treated_by`、`contraindicated_for`、`requires_exam`、`belongs_to_dept`、`subclass_of`、`aligned_to_standard`。

> **版本号口径**（两套号不混用）：`schema` 用 `v0` / `v1`，指实体与关系的**结构**；本体快照用 `v0.9` / `v1.0` / `v1.1`，指**数据**。
> 链路：W1 `schema v0` 冻结 + 种子 `v0.9`（待审，不进线上）→ W3 发布 `v1.0` → W4 演示进化出 `v1.1`。差分报告写「v0.9→v1.0」和「v1.0→v1.1」，不写「v0→v1」。

每条三元组带元数据：

~~~json
{
  "triple_id": "T-000912",
  "head": {"id": "K27", "type": "Disease", "label": "消化性溃疡"},
  "rel": "requires_exam",
  "tail": {"id": "EX-HP-BT", "type": "Exam", "label": "幽门螺杆菌呼气试验"},
  "confidence": 0.86,
  "provenance": {"asset_id": "AST-2026-000137", "anchor_id": "AST-2026-000137#p3.t1.r2",
                 "source_type": "pathway"},
  "standard": {"scheme": "ICD-10", "code": "K27"},
  "status": "active",
  "version_added": "v1.0",
  "version_removed": null
}
~~~

`provenance` 是硬要求：**没有出处的三元组不许进本体**。这一条同时解决 R2 的「对齐」和 R4 的「溯源」——本体本身就是证据的一种。

`source_type` 固定三值，用来锁死「这条知识该由谁背书」：

| 取值 | 含义 | 能承担什么 | 不能承担什么 |
| --- | --- | --- | --- |
| `icd10` | 编码表映射 | 症状 / 诊断 → 编码的归一 | 任何病种间的鉴别、检查项推荐 |
| `pathway` | 临床路径 / 诊疗指南 | 症状 → 病种的鉴别入口、病种 → 检查项 | 药品禁忌 |
| `drug_label` | 药品说明书 | 禁忌、不良反应、相互作用 | 诊断与检查 |

抽取与查询两侧都按这张表校验：`kg_query` 返回鉴别路径时，若路径上的边不是 `pathway`，标 `weak_evidence` 并降置信度。

### 5.2 低资源半自动构建：四步流水线

~~~
新文档 → ① 候选抽取 → ② 规则校验 → ③ 标准对齐 → ④ 人工确认 → 发布 vN+1
             (LLM)        (确定性)      (映射表)      (Web 表单)
~~~

**① 候选抽取（LLM + 少样本）**
用 3–5 个标注样例做 few-shot，让模型从段落里抽 `(head, rel, tail, 出处句)`。低资源的关键不是模型，是**约束输出空间**：只允许上面 6 类实体、8 类关系，超出直接丢弃。

**② 规则校验（确定性，不调模型）**
五条硬规则：

- 头尾实体必须能落到已有节点或 ICD-10 编码，否则转「待建节点」队列
- 关系与实体类型必须匹配（`requires_exam` 的头必须是 Disease，尾必须是 Exam）
- 同一 (head, rel, tail) 已有 active 记录则判重复，不新增
- 与已有记录语义冲突（如 `contraindicated_for` 与 `treated_by` 同时成立）标冲突，进人工队列
- 段落长度 < 30 字或全是表头的，不抽

这一步把 LLM 的噪声挡掉大半，也让抽出来的东西可解释。

**③ 标准对齐**
维护 `alias_map`：自由文本 → ICD-10 编码 / 临床路径条目。对齐失败的进「未对齐队列」，这部分数据本身就是一个可讲的点——低资源场景下对齐率本来就是瓶颈，我们给出对齐率的量化曲线。

**④ 人工确认（不可省）**
一个小 Web 页（或直接 CLI），把候选三元组以 diff 形式列出：`+ 新增 12 条 / ~ 修改 3 条 / - 废弃 1 条`。确认后写快照，版本 +1。

> 为什么必须有这一步：全自动更新的本体在医疗场景不可接受，而且评审一定会问「模型抽错了怎么办」。把人工确认做成产品的一部分，比假装全自动更可信。

### 5.3 版本与差分

| 机制 | 实现 |
| --- | --- |
| 快照 | 每次发布把全量三元组导成 `ontology/v1.0.jsonl` + 生成 `manifest.json`（条数、hash、时间） |
| 差分 | `onto diff v1.0 v1.1` 输出 added/modified/removed 三张表，带 provenance |
| 回滚 | 指针指回旧快照，MCP 工具读指针，不读硬编码路径 |
| 触发 | 三条件任一：新文档入库数 ≥10；人工发起；每周定时 |

这个设计有个直接好处：演示时可以先跑一遍评测拿到 v1.0 的成绩，现场走一遍「新文档 → 本体进化 → v1.1」，再跑同一套评测，让分数变化出现在屏幕上。这是「可进化」最有力的证据。

### 5.4 冷启动

冷启动不依赖任何未落地的数据。可用的是三类公开材料，抽取规则自己写：

1. **ICD-10 编码表**（约 2.6 万条）→ 抽 `(症状/诊断) -aligned_to_standard-> (编码)`，纯映射，规则可穷举，`source_type = icd10`
2. **卫健委临床路径**（15 份）→ 抽 `(病种) -has_symptom-> (症状)`、`(病种) -requires_exam-> (检查项)`，`source_type = pathway`，provenance 指 PDF 页码
3. **药品说明书**（20 份）→ 抽 `(药品) -contraindicated_for-> (病种)`，`source_type = drug_label`

统一口径：`confidence` 取 0.9（有原文原句支撑）或 0.6（仅规则匹配）；`version_added = "v0.9"`。v0.9 是「待审种子」，不进 v1.0，等人工抽查 200 条后按通过率决定是否并入。

规模目标改为**质量优先**：首批抽到 3000–10000 条就足够支撑两跳查询。不设「凑够 8 万条」这类没有评测意义的指标——三元组条数不是评分项，查得准才是。

**关于 OpenCMKG**：该数据集确实存在（公开报道口径约 35 万三元组），但我们的仓库里没有它的数据文件，且其许可限定学术研究用途（见 `medpal/docs/handoff/W2-T-zincumyu-知识图谱纯算法与LLM选节点.md:55`）。若后续拿到可再分发许可，可作为加速项并入 v0.9；拿到之前，方案不依赖它，也不写进任何里程碑。

## 6 工具层：MCP Server 规格（R3 前半）

### 6.1 服务形态

- 语言：Python 3.12 + FastMCP（或官方 `mcp` SDK 的 streamable-http）
- 监听：`0.0.0.0:8090`，路径 `/mcp`
- 鉴权：Bearer Token（Nexent 远程链接填 Authorization header）
- 同时导出 `openapi.json`，作为「API 转 MCP」的备用接入方式
- 无状态优先，唯一的持久状态是 SQLite 与版本指针

### 6.2 十个工具（核心 7 + 辅助 3）

| 工具 | 入参 | 出参 | 用途 | 对应要求 |
| --- | --- | --- | --- | --- |
| `ingest_asset` | path, modality?, source_meta | asset_id, anchors, kb_status | 解析一份文件，生成 Asset Card，投递到指定知识库 | R1 |
| `get_asset_card` | asset_id 或 query | card 列表 | 按模态/来源/实体查资产 | R1 |
| `kg_query` | seed_entities, max_hops=2, rel_filter? | paths[], triples[] | 本体多跳查询，返回带 provenance 的路径 | R2/R4 |
| `onto_propose` | asset_ids[], scope? | candidates{diff}, confidence | 从新文档抽候选三元组，产出待审 diff | R2 |
| `onto_commit` | diff_id, approve_list | version, manifest | 确认并发布新版本 | R2 |
| `std_align` | entity_text 或 triple_id | icd10?, pathway?, alias_hit | 与 ICD-10 / 临床路径对齐，返回映射与未对齐原因 | R2 |
| `trace_write` | question, steps[], answer | trace_id, report_path | 写决策链，产出可导出的报告 | R4 |

外加三个辅助工具：`skill_export`（把 trace 转成 Skill 模板草稿）、`kb_search`（透传 Nexent 混合检索，供脚本类技能调用）、`health`（存活与版本自检，部署与演示兜底用）。

**对外口径固定为「10 个工具（核心 7 + 辅助 3）」**，与 `agent/mcp-server/server.py` 的注册数一致。全文不再出现「7 个工具」「10 个工具」混用。

### 6.3 设计约束

- **所有出参必须可序列化且带 id**：任何结论都要能对上 `asset_id` / `anchor_id` / `triple_id`，否则下游没法溯源
- **工具不做长推理**：单个工具执行 < 5s，推理留给智能体层。这样超时好定位
- **错误显式**：找不到证据时返回 `{"ok": false, "reason": "no_evidence", "hint": "..."}`，不返回空数组让模型瞎猜
- **可单测**：每个工具都有 pytest 用例，跑 `pytest -q` 不依赖 Nexent 在线

~~~python

def kg_query(seed_entities: list[str], max_hops: int = 2,
             rel_filter: list[str] | None = None,
             version: str = "latest") -> dict:

    返回 {"ok": bool, "version": str, "paths": [{"nodes":[...], "rels":[...],
    "provenance":[{"asset_id":..., "anchor_id":...}], "score": float}]}
    """
~~~

### 7.2 三个技能各干什么

| 技能 | 触发语 | 编排的工具序列 | 产物 |
| --- | --- | --- | --- |
| **S1 资产清点** | 「盘点这批文件」「看看这批资料有什么」 | `ingest_asset` × N → `get_asset_card` 汇总 → 生成 Markdown 台账 | 资产台账 + 缺失告警（模态不全/解析失败） |
| **S2 本体进化** | 「把这些文档里的新知识并进本体」 | `onto_propose` → `std_align` → 展示 diff → 等人工确认 → `onto_commit` | diff 报告 + 新版本号 + 对齐率 |
| **S3 跨文档取证** | 「这个病人该去哪个科、做什么检查」 | `kg_query` → 检索知识库 → 冲突检测 → `trace_write` | 建议 + 决策链报告 |

### 7.3 S3 的检索-推理双驱动怎么写清楚

这是赛题原词「检索-推理双驱动协同智能体执行流」，必须给出机制而不是口号：

~~~
Loop (最多 4 轮):
  1. 检索：从当前实体集合出发，kg_query 拿 2 跳路径 + 知识库混合检索拿段落
  2. 判断：证据够不够回答？
       - 够 → 进入推理
       - 缺 X 类证据 → 生成子查询，回 1
       - 两轮无新增 → 降级输出「证据不足」并列出缺什么
  3. 推理：在证据集合上做结论生成，每一步必须引用 anchor_id
  4. 冲突检测：同一结论有反向证据 → 标冲突并降置信度
  5. 落链：trace_write
~~~

「双驱动」的落点是 **步骤 2 的判断**：检索不是一次性投喂，推理会反过来生成新的检索需求。这条要在 PPT 里用一张循环图讲，比堆十页架构图有用。

### 7.4 SKILL.md 示例（S3）

~~~markdown
---
name: evidence-decision
description: 基于院内多模态资产，对门诊主诉给出科室与检查建议，并输出可溯源的决策链
allowed-tools: [kg_query, std_align, trace_write, kb_search, vision_ocr]   # 平台 VLM 工具名未确认（风险 R-02），暂用 vision_ocr 占位
~~~

### 8.2 报告输出

一键生成 Markdown/HTML 报告，结构固定：**结论 → 置信度 → 证据表（anchor_id + 原文摘录 + 出处）→ 决策链时序 → 缺口说明**。报告可直接作为答辩材料，也可以给医生看。

### 8.3 可复用性怎么体现

- 同一份 trace 可导出成 Skill 模板草稿：把步骤序列抽成 SKILL.md 的「步骤」段，把工具调用抽成 `allowed-tools`

- 演示话术：「换一个科室，只需要改模板里的实体范围和证据门槛，不用改代码」

## 9 评测（决定名次的部分）

### 9.1 指标

| 指标 | 定义 | 目标（v1.0） |
| --- | --- | --- |
| 答案准确率 | 与人工 gold 的科室/检查项一致率（分级计分） | ≥ 70% |
| 证据召回率@k | gold 证据中被引用到的比例 | ≥ 80% |
| 溯源完整率 | 有 anchor_id 且能点回原文的结论占比 | ≥ 95% |
| 本体增量准确率 | 新增三元组人工抽查通过率 | ≥ 85% |
| 标准对齐率 | 实体成功映射到 ICD-10 的比例 | ≥ 75%，并给出曲线 |
| 平均时延 | 单次问答端到端 | ≤ 30s |

### 9.2 评测集怎么来（50 条；W2 起草、W3 定稿）

- 30 条：人工新写（现有 65 个是代码级单测，不能改写成问答，只能当回归网）
- 15 条：人工新写，覆盖跨 3 类文档的多跳
- 5 条：反例题（证据不足，正确答案是「无法判断 + 缺口说明」），专门测幻觉

每条标注：问题、gold 结论、gold 证据 anchor 列表、难度、涉及跳数。

> **排期口径**：50 条不是一周从零写完的。W2 由 T5 起草 20 条（含多跳 15 条里的 10 条），W3 补齐其余 30 条并全量跑、出误差分析。「一周定稿并跑完」成立，「一周从零写完」不成立。

### 9.3 双轨评测

1. **离线脚本**：`eval/run_eval.py` 直连 MCP + 模型 API，跑全量、出 JSON + Markdown 报表。日常回归用这个，快、便宜、可进 CI。
2. **Nexent 评估**：把 50 条导入智能体评估，用平台评估器跑一遍，截图进答辩材料。评委认平台内的结果。

两套结果**不要求一致**：离线脚本是规则实现，Nexent 内是大模型实现，这是两条不同的实现路径，差异只能说明「实现不同」，不能解释成「智能体层损耗」。真要谈损耗，只能在**同一条链路**上做开关对比（关模型 / 开模型各跑一遍），因果才成立。

**离线基线已经存在**（2026-10-22 实跑）：14 条上科室 100%、检查项 Jaccard 100%、冲突召回 100%、证据召回 100%、溯源完整率 100%、平均时延 12ms。这个分数**不能拿去当答辩分数**——它跑的是规则化链路，不含大模型，题也是我们自己出的。它只有两个用途：①当回归网，任何人改 store/parsers 后分数掉了立刻知道；②当上限参照，用来看「大模型链路离规则链路差多远」，作为工程判断，不当性能结论。

## 11 「小而精」的边界：明确不做什么

写在 README，答辩时主动说，比被问出来好。

| 不做 | 原因 |
| --- | --- |
| 不做终端硬件、不做 APP | 赛题不要求；硬件周期不可控 |
| 不做影像 AI（CT/X 光判读） | 需要 GPU 与标注数据，四周做不出可信结果 |
| 不做多行业 | 一个行业的机制讲透，比四个行业各讲一半得分高 |
| 不做真实 HIS/EMR 对接 | 无授权环境；用样本数据等价演示 |
| 不做全自动本体更新 | 医疗场景不可接受；人工确认是我们的设计选择，不是妥协 |
| 不做自研向量库/自研 RAG | 平台已有，重复造轮子不加分 |
| 不做独立前端工程 | 用 Nexent 自带界面 + 一个 Streamlit 台账页 / 决策链报告页；W2–W4 的可视化都长在这两个页面里，不另写前端工程 |
