## 1 已经定死的，不再讨论

这四项在 02 号、ws-protocol.md、11 号三份文档里**完全一致**，不是争议点：

| 参数 | 取值 | 出处 |
| --- | --- | --- |
| 采样率 | **16000 Hz** | 三份文档一致 |
| 位深 | **16 bit（小端 PCM）** | 三份文档一致 |
| 声道 | **单声道** | 三份文档一致 |
| 帧长 | **200 ms** | 三份文档一致 |

由这四个数推出来的固定值（算一次，双方都按这个校验）：

| 派生值 | 结果 |
| --- | --- |
| 每帧字节数 | 16000 × 2 B × 0.2 s = **6400 B** |
| 每秒帧数 | **5 帧** |
| 每秒字节 | 32000 B/s ≈ 31.2 KB/s ≈ **256 kbps** |
| 每帧安全上限 | 接收端**建议**按 ≤ 8192 B 校验，超了立即丢弃并记 `E_TURN_OUT_OF_ORDER` |

> 采集端最容易错的点：`getUserMedia` 的 `sampleRate` 只是**建议值**，浏览器可能给 44100 或 48000。T2 侧必须显式重采样到 16000 再切帧，不能假设拿到的就是 16k。

## 2 封装开销：为什么建议二进制帧

同一段音频，两种封装的实际体积（按 15 分钟一次陪诊算）：

| 项 | base64 塞进 JSON | 二进制帧 |
| --- | --- | --- |
| 每秒 | 41.7 KB/s（膨胀 33%） | 31.2 KB/s |
| 15 分钟一次陪诊 | **36.6 MB** | **27.5 MB** |
| 每帧 | 8536 B（base64 后含填充） | 6400 B |
| 服务端额外开销 | 每帧一次 base64 解码 | 无 |

结论：**延迟与内存都按 15 分钟连续传计算的话，二进制帧更省**，而且 WS 协议原生支持二进制帧，不需要额外编码层。

## 3 待裁决的两处（今晚要定）

### 3.1 封装形式

| 选项 | 现状 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 二进制帧 | 11 号 §6 采用 | 省 33% 流量与一次解码；WS 原生支持 | W1 的 mock 要区分文本帧与二进制帧 |
| B. base64 塞 JSON | `ws-protocol.md` 采用，`tools/mock_ws.py` 已按此实现 | W1 调试方便，`websocat` 直接粘贴可见 | 长期多传 9 MB/次，且每帧要解码 |

**建议：W1 先维持 B（mock 已跑通，不返工），W3 会话客户端落地时切 A，切的时候把 `ws-protocol.md` 版本号从 v0.1 提到 v0.2。**
理由：W1 只验证协议形状，不传真音频；真音频要到 W3 才有采集端。现在改 mock 没有收益，但**必须在 W3 前改**，否则 15 分钟会话会多背 9 MB 和每帧一次解码。

若双方不接受"先 B 后 A"，则 W1 直接上 A——代价是 `tools/mock_ws.py` 与冒烟测试各改一次，约 1 小时。

### 3.2 字段命名

| 用途 | `ws-protocol.md` | 11 号 §6 | 建议统一为 |
| --- | --- | --- | --- |
| 按键 | `key`，取值 `GREEN_DOWN`/`GREEN_UP`/`RED_LONG`/`SIDE` | `button.event`，取值 `green`/`red`/`side` | **`GREEN_DOWN` 这套常量**（设备端已有四按钮对应，且大写下划线符合 19 号的状态枚举命名习惯） |
| 音频分片 | `audio`，字段 `session`/`seq`/`payload` | `audio.chunk`，二进制帧 | **`audio` + `seq`**（W3 切二进制后 payload 改为二进制帧） |
| 续传 | 「按 session + 最后 turn 续传」 | 「重发 `session.hello`，按 `episode_id` 取最新状态」 | **两者都要**：重连先握手（带 `episode_id`），再按最后确认的 turn+1 续播 |

## 3.5 实调发现：TTS 输出与 ASR 输入的真实形态（2026-10-20 实测）

这一节不是讨论，是把实测结果写死，双方按它实现：

| 事实 | 数值 | 影响 |
| --- | --- | --- |
| TTS 输出采样率 | **24000 Hz** / 16bit / 单声道 | 与协议约定的 16000 Hz 不一致，**播放前必须降采样**，否则语速听感与时长都对不上 |
| ASR 接受的输入 | **24000 Hz 可直接喂**，服务端不要求先重采样 | 采集端省一次重采样不代表可以直接上传采集流的 48kHz；仍按 16k 采集与切帧 |
| TTS 返回的 WAV 头 | `data` 块声明长度是 **0x7FFFFFDB**（约 2GB 占位值） | **不能用 WAV 头算时长或分帧**。`wave` 模块会读出 44739 秒这种荒谬值；一律按实际文件字节数 ÷ (采样率 × 2) 计算 |
| 时长口径 | 3.68 秒音频 = 176640 字节 ÷ (24000 × 2) | 与 `usage.seconds=3` 对得上（服务端按整秒计费） |

**责任划分补充**：降采样（24k → 16k）由 **T5 在适配器层**做，不塞给设备端——设备端只管采集与播放，不承担格式转换（与 02 号「设备端不得包含业务判断」一致）。

## 4 各自职责边界

| 谁 | 负责 | 明确不做 |
| --- | --- | --- |
| **T2（采集端）** | ① `getUserMedia` 约束（`channelCount:1`、`echoCancellation:true`、`noiseSuppression:true`、`autoGainControl:true`）；② 重采样到 16000 并切 200ms 帧；③ 单调递增 `seq`；④ **保留最近 30 秒帧**用于补发；⑤ 断线重连后先握手再续传；⑥ 播报期间按键要发 `control.barge_in` | 不做语音识别、不做置信度判断、不解析医学内容 |
| **T5（适配器端）** | ① 接收 `pcm: bytes` + `sample_rate` 参数（现有接口 `Asr.transcribe(pcm, sample_rate=16000)`）；② 不假设位深与字节序，按 16bit 小端解析；③ 上游超时 2 秒、只对网络错误重试一次；④ 置信度 < 0.6 抛 `LowConfidence` 走求证；⑤ TTS 输出**语速约 0.7–1.0 倍、按句判定**（不再承诺固定 0.86），断句按标点 | 不做切帧、不做回声消除、不碰设备端 UI |

**接口契约以代码为准**（已存在，不用再设计）：

```python
# backend/adapters/base.py
class Asr(Protocol):
    async def transcribe(self, pcm: bytes, sample_rate: int = 16000) -> AsrResult: ...

class Tts(Protocol):
    async def synthesize(self, text: str, rate: float = 0.86) -> bytes: ...
```
