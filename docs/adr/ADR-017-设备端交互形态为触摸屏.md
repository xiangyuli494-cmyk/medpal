# ADR-017 设备端交互形态采用 10.1 寸触摸屏

- 状态：已接受（W1）
- 日期：W1

## 1 背景

设备端是本项目的产品本体：一台放在门诊大厅、由老人自己使用的陪诊终端。它的交互形态必须先定下来，因为它同时决定三件事——硬件的物料与结构、会话协议的上行消息形状、界面信息架构的写法。

约束有四条：目标用户是不熟悉智能设备的老人与视障、听障人群；外观必须一眼看懂「下一步做什么」；硬件是条件交付，结构与开模成本要可控；W1 结束时必须有一套能写进文档、W2 就能照着实现的确定形态。

---

## 2 备选方案

| 方案 | 内容 | 判断 |
| --- | --- | --- |
| A | 12 个物理按键 + 语音，每个功能一个键 | 否决。开模、丝印、导光、防水、寿命测试全都要做；且 7 个功能键（电源、音量±、语速±、主菜单、返回）对老人是干扰，混在主界面里只会增加误触 |
| B | 3 个物理键（绿/红/侧），其余功能走语音 | 否决。语音识别失败时无兜底路径；「主菜单」这类导航动作没有物理入口 |
| C | 3 个键 + 屏幕软键盘 | 否决。软键盘的前提就是触摸屏，等于承认触摸是唯一交互面，却还留着三个键的机械成本 |
| D | **10.1 寸竖屏触摸屏，全部交互在屏幕上；协议用 `touch.event`** | **采纳** |

---

## 3 决策

1. **设备形态**：10.1 寸竖屏触摸屏（800×1280 物理像素，逻辑视口 480×800），Chromium Kiosk 全屏，零打字，触摸 + 语音。机身侧面仅有物理电源开关，用途是维护断电，**不进入交互设计与协议**。
2. **交互模型**：常驻底栏 4 个控件（`mic` / `back` / `menu` / `sos`）+ 屏内主操作 `primary` + 选项胶囊 `option:<slot_id>` + 设置面板。主流程只用 2 个控件（`mic` 与 `primary`）。
3. **协议**：上行消息为 `touch.event`（`target` + `action`），`action` ∈ `tap` / `long_press`。`dialog.reply` 带 `primary_label`，主操作按钮的文案由服务端下发。
4. **硬性规格**：最小点击区 88×88 CSS px，控件间距 ≥16px，正文 ≥24px，标题 ≥19px，触摸至页面反馈 <200ms。**禁止手势**——不滑动切页、不双击、不双指；唯一的长按是一键求助，且「3 秒内单击两次」等价。
5. **不引入键盘等价键**：浏览器里用鼠标点击即可调试，不维护一套 `F1`–`F12` 映射。

---

## 4 依据

1. **设备上只该出现「下一步」。** 电源、音量、语速、主菜单、返回都是维护或导航动作，收进底栏与设置抽屉后，主屏可以只留一个通栏大按钮。触摸屏是唯一能做到这种分层的形态。
2. **触摸屏省掉整个结构与开模链路。** 硬件为「树莓派 Zero 2W + 10.1 寸触摸屏 + 震动马达 + 外壳」，C3 只做触觉反馈模块，硬件工作量实质下降，与 ADR-014 把硬件降为条件交付的口径一致。
3. **触摸是老人已经在用的交互。** 目标用户不会用智能手机的复杂功能，但「点一下屏幕上写着字的方块」是移动时代之后最通用的心智模型；物理小键反而需要学习。
4. **`primary` 把「下一步」变成服务端的责任。** 同一个按钮在 `BRIEFING` 是「我听明白了」，在 `REGISTER` 是「确认挂号」，在 `RECAP` 是「对，记住了」。若由设备端自己映射，等于把状态机搬进客户端，违反「设备端只做渲染与采集」的既有约束。文案由 `primary_label` 下发、设备端只回传 `target`，这条边界才守得住。
5. **W1 阶段落地成本最低。** W1 无任何客户端实现，协议与信息架构都还是文档，确定形态只影响 `tools/mock_ws.py` 与文档。

## 6 待办

- 触摸目标尺寸审计：`device-ia.md` §2.5 给了规格，需要在 W2 逐屏骨架出来后用脚本实测一遍（每个可点元素的 `getBoundingClientRect()`）。
- 震动反馈的语义在 C3 触发时定：现在是「确认短震两下 / 出错长震一下」，是否保留取决于震动马达是否到货。
- `demo/device-prototype.html` 的左侧演示控制台是「按命令名驱动」的调试面板，与真机的触摸路径不同。W2 起应补一条「只用底栏与主操作走完一遍」的演示脚本，证明不靠调试面板也能演示。
