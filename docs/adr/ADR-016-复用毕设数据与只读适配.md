# ADR-016 · 复用毕设数据与只读适配，不改旧系统

| 项 | 内容 |
| --- | --- |
| 编号 | ADR-016 |
| 标题 | 复用毕设数据与只读适配，不改旧系统 |
| 状态 | 已采纳 |
| 决策日期 | W1 |
| 责任人 | T1 |

## 背景

毕设是一套可运行的 Django 医疗系统（8001，32 张表），带着 743 条检查项与院内方位、33 个科室、真实排班结构。8 周内从零造这套数据不现实：科室与楼层信息是医院的，检查项目录有 1700 多条，手工编不出来。

同时旧系统有七个安全债（AllowAny、明文密码、硬编码 token、并发超卖、不可逆加密、无外键、CSRF 不一致），任何一条都不适合带进新系统。

## 备选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| A 全量迁移旧系统，在其上改造 | 数据现成，功能看起来多 | 要背着七个安全债改；LangGraph 症状问答与陪诊域无关；8 周不够 |
| B 完全新写，不使用旧系统 | 干净，无历史包袱 | 缺真实科室/检查项/方位数据，演示像空壳；手工编数据要两周 |
| C 只读调用 + 一次性导出数据，业务全新写 | 数据真实，边界清楚，随时可切断 | 要写导出脚本与降级路径，多一层适配器 |

## 决策

采纳 **方案 C**：

1. 一次性导出检查项（含方位）、科室字典、排班样例到 fixtures/legacy/，进仓库；
2. 实时查询走 backend/adapters/legacy/ 的只读 HTTP 客户端，失败降级到 fixtures；
3. 旧系统一行代码不改，端口 8001 保留；
4. 旧系统的鉴权、密码、加密、检索栈一律不沿用。

## 依据

1. 数据是真实医院的，不是编的，这是答辩时唯一能证明「我们懂业务」的东西；
2. 检查项带方位（门诊三楼B区306），正好喂给检查规划引擎，省掉最贵的一环；
3. 只读调用可以随时切断：旧系统挂了，演示照样能跑；
4. 不改造旧系统，就不必先还它的技术债，8 周内这是唯一可行的路径。

## 影响与代价

| 项 | 影响 |
| --- | --- |
| 部署 | 演示需要旧系统可选运行；不运行也能演示（fixtures 兜底） |
| 测试 | 适配器必须有降级测试，不能只在旧系统开着时通过 |
| 数据 | 导出脚本写死三张表白名单，禁止导出 user / registration / chat / checkpoints |
| 维护 | 旧系统一旦停机，只需要删一个目录，不影响主链路 |
| 团队 | T1 负责导出与适配器；T6 负责一条「旧系统不可用」的端到端用例 |

## 八周工期下的影响

- W1 完成导出（已做）与密钥轮换；
- W2 与旧系统联调一次 find_location，把契约写死；
- W3 起新系统自己建表，旧系统只提供方位查询；
- W6 后如果不再需要，适配器降级为「演示兜底」，答辩时不依赖它。
