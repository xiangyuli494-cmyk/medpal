## 一句话说清它干什么

把散在六处的合并要求收成一页，让新人不用翻规范就知道交什么才能合。

## 数据流

来源：12 号 §2、13 号 §3.2、docs/handoff/README.md、两个 workflow 文件、tools/check_handoff.py、以及 GitHub 分支保护设置。

这六处 → 人工比对 → 写成 docs/合并规则.md 的三段（机器查什么 / 人要做什么 / 被拦了怎么查）→ CONTRIBUTING 与 PR 模板各加一条入口 → 读者从任何一个入口都能抵达同一页。

~~~mermaid
flowchart LR
  A[12/13 号规范] --> M[docs/合并规则.md]
  B[两个 workflow] --> M
  C[check_handoff.py] --> M
  D[分支保护设置] --> M
  M --> E[CONTRIBUTING §5]
  M --> F[PR 模板顶部]
~~~

## 我改了什么（人工修改点）

1. 六处口径逐条对照，发现 12 号与 13 号对分支寿命说法不同（1 周 vs 3 天），规则页只写 1 周，冲突另记。
2. 把「strict 模式下 main 一动就要 rebase」这条单独写成第 5 个绿灯，因为它是代码没问题也会被拦的唯一原因。
3. 写出已知盲区：Makefile、pyproject.toml、requirements*.txt、.gitignore 不触发交接单检查，避免读者以为规则是全覆盖。
4. PR 模板顶部的入口用相对路径，指向 docs/合并规则.md，避免以后挪文件时链接失效。

## 怎么验证的

| 验证方式 | 具体内容 |
| --- | --- |
| 人工核对 | 本 PR 自身即触发 handoff 检查（改了 .github/ 下的文件），能过即证明规则可执行 |
| 链接检查 | CONTRIBUTING 与会话手册中的相对路径在同一 PR 内可点开 |
| 文档一致性 | 第七节的保护设置与 Settings 当前值逐项比对过 |

## 已知风险与留待后续

- 规则页第七节需要随分支保护设置同步更新，靠人记；
- 盲区（Makefile 等）是否纳入检查，留给 W2 评审决定。
