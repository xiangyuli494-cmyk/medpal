## 一句话说清它干什么

读两个版本的本体快照，输出「新增 / 删除 / 修改 / 编号漂移」四类结果：`--format json` 给 T3 页面直接接，`--format text` 给人读，一条命令看清这一版知识到底动了什么。

## 数据流

`agent/mcp-server/data/ontology_<版本>.jsonl` 两个文件 → 按 schema §4.1 的主键 `triple_id` 各建一个字典 → 集合运算分出「只新版有」「只旧版有」「两边都有」→ 对「只新版有」的编号再按业务键 `(head_id, rel, tail_id)` 对账，能对上旧版的算「编号漂移」而不是「删一条加一条」→ 交集逐条比「两侧快照都带的字段」（现在只有 `confidence`、`anchor_id` 与三个内容列）判定是否算「改」→ 组装 `counts + added + removed + modified + id_drift + identity + compared_fields` → 按 `--format` 渲染成 JSON 或中文报告。全程只读文件，不连数据库、不调 MCP。

~~~mermaid
flowchart LR
  A[ontology_old.jsonl] --> C[按 triple_id 建索引]
  B[ontology_new.jsonl] --> D[按 triple_id 建索引]
  C --> E{按编号求差}
  D --> E
  E -->|只新版有| E2{业务键能在旧版找到?}
  E2 -->|能找到| J[id_drift]
  E2 -->|找不到| F[added]
  E -->|只旧版有| G[removed]
  E -->|两边都有| H{逐字段比差异}
  H -->|有变化| I[modified]
  F --> K[counts + render_report]
  G --> K
  I --> K
  J --> K
~~~

## 我改了什么（人工修改点）

1. 新增 `agent/ontology/diff.py`：`signature()` 取业务键（只用于对账）、`changed_fields()` 比字段、`diff_versions()` 出四类结果、`render_report()` 出中文报告、`main()` 提供 CLI（`--base/--target/--format`）。
2. 身份以 `ontology-schema.md` §4.1 的主键 `triple_id` 为准：增 / 删 / 改都按编号判定，与 schema 字段表一致，也方便 T3 直接按 `triple_id` 对上 `kg_query` 的返回。
3. 但编号不稳是上游事实（`store.add_triple()` 用 `uuid4()` 随机生成，重建库或重新抽取后同一条知识会换号），所以补一步对账：新版里的陌生编号，若业务键 `(head_id, rel, tail_id)` 在旧版存在且旧编号没出现在新版，判为「编号漂移」而不是「删一条加一条」。schema §8 第 3 条把业务键定为判重键，正说明同一业务键在库里只有一行，这个推断才有依据。
4. 编号漂移单独放进 `id_drift`，不计入 `modified`，也不计入 `counts`——留痕但不制造噪音；若一条知识既换号又改内容，则 `id_drift` 与 `modified` 各记一条，两个事实都不隐瞒。
5. `to_record()` 作为对外字段名的唯一出口，按 `ontology-schema.md` §4.2 输出 `head` / `tail` 嵌套与 `provenance.anchor_id`；快照只给 id 级信息，拿不到的 `type / label / standard / version_added` 不输出，不臆造。
6. 不 import `store.diff_versions()`：它只有「按编号求差」一步，没有对账，重建库时会给出 17 删 17 加；本模块独立实现，避免被它的语义绑住，也不修改 `store.py`（T2 的内核，只读）。
7. 只比「两侧快照都带」的字段：`comparable_fields()` 先从实际行里收集出现过的键，再决定比哪几个，结果写进 `compared_fields`，报告末尾也用一行注明未比对字段——不留「永远不触发」的死判据，也不让「无变化」被读成「所有字段都一样」。
8. 主键校验：快照缺 `triple_id` 或同一文件里编号重复，抛 `DiffVersionInvalid` 并指出文件与行号，不静默丢行。
9. 新增 `agent/tests/test_ontology_diff.py` 18 个用例，全用临时 JSONL 文件，离线可跑。
10. 过程是先红再绿：首轮先写测试看到 `ModuleNotFoundError: No module named 'agent.ontology'` → 写实现 → 被 `KeyError` 逼出契约调整（`modified` 记录从 `key` 数组改成扁平字段，随后按 schema §4.2 统一成嵌套结构）。本轮把判等键从业务键改成 `triple_id` + 业务键对账，代码与测试同批改，其中一条测试的预期写错了（以为换号后只能报「加一条」），实跑后被对账逻辑判成「漂移 + 修改」，按实际行为改正了测试。

## 已知风险与留待后续

- **`removed` 的真实性依赖废弃能力**：`store.py` 的 `status` 只写 `active`，`version_removed` 建了列但从不赋值，`snapshot()` 又只导 `status='active'`。因此在「同库累加」的正常流程下 `removed` 恒为空；删除栏要等 T2 补上废弃标记后才可信。已把修法建议给 T2（`UPDATE triple SET status='deprecated', version_removed=?`），`snapshot()` 与本模块均无需改动。
- **两套数字仍会在「重建库」场景分叉**：身份现在两边都是 `triple_id`，日常同库累加结论一致；差别在本模块多一步业务键对账，所以重建库（`seed --reset`、换机重灌、重新抽取）时 `store.diff_versions()` 报「删 17 + 加 17」，本模块报「0 变化 + 17 条编号漂移」。两种口径都对同一事实的不同说法，需要在统一对外数字前与 T2 对齐；根治办法是 `add_triple()` 改用确定性编号，届时本模块的 `id_drift` 会自然为空。
- **编号不具跨库稳定性，已有实测**：schema 附录 A 里的 17 个 `triple_id` 与仓库 `ontology_v0.9.jsonl` 的 17 个编号交集为 0（内容逐条对得上）。建议附录 A 补一行「编号仅示意，跨版本对照请用 `(head, rel, tail)`」，已同步给 T1。
- **快照字段不足（含两处读不到的 schema 要求字段）**：schema §4.2 的 `head.type` / `head.label` / `tail.label` / `standard` / `version_added` 快照里没有，本模块缺省不输出；schema §10 要求 T4 读 `status` 与 `version_removed`，而 `snapshot()` 只 SELECT 7 列，这两个字段实际读不到。当前处理：`compared_fields` 如实声明比了哪几列，报告末尾注明 `standard 不在快照中，本次未比对`。若后续 `snapshot()` 扩列，`_entity()` 与 `changed_fields()` 会自动跟上，无需改本模块。
- **CI 未覆盖**：`ci.yml` 的单元测试只跑 `backend/tests`，本模块用例在 `agent/tests`，目前需本地跑（已向 T6/T1 提出扩成 `pytest backend/tests agent/tests`）。
- **格式归属**：schema v0 已于 2026-10-29 冻结并随 PR #32 合入 main，但其中没有「差分报告」一节，本格式仍由 T4 先定，待 schema v1 增补（候选 §4.4）。字段名若有变更只改 `to_record()` 一处。
- **不依赖 2.4**：本模块输入是快照文件，比对逻辑自包含，不依赖 T2 的 2.4（11-08）版本化内核；2.4 交付后若内核接口变化，以本模块已发布的格式为准做对齐。
