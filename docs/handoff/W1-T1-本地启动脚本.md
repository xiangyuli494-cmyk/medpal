## 一句话说清它干什么

让任何人一条命令就能起两个假服务（8000 / 8090），不再被「python 是占位符」卡住。

## 数据流

`tools/dev.ps1` 先挑解释器（仓库内 `.venv` → `venv` → PATH 上的 python，跳过商店占位符），验版本、验 `websockets`，再逐个查端口占用，空闲才 `Start-Process` 拉起 `tools/mock_api.py` 与 `tools/mock_ws.py`；随后轮询 `/api/v1/health` 与 8090 的 TCP 端口确认真的起来了，最后打印地址与 PID。

~~~mermaid
flowchart LR
  A[dev.ps1] --> B{挑解释器}
  B -->|.venv / venv / 真 python| C[验版本 + 依赖]
  B -->|WindowsApps 占位符| X[报错退出 1]
  C --> D{端口空闲?}
  D -->|否| E[跳过并提示已在跑]
  D -->|是| F[Start-Process mock_api 8000]
  D -->|是| G[Start-Process mock_ws 8090]
  F --> H[轮询 health]
  G --> I[轮询 TCP 8090]
  H --> J[打印地址 + PID]
  I --> J
~~~

## 我改了什么（人工修改点）

1. 原脚本裸调 `python`。装了 Microsoft Store 版 Python 的机器上，PATH 里的 `python.exe` 是占位符：有命令、无解释器，传任何参数都以 9009 退出，两个服务根本起不来。改成优先用仓库内 `.venv\Scripts\python.exe`，其次 `venv`，最后才用 PATH 上的 python，并显式跳过 `*\WindowsApps\*` 路径。
2. 原文件是无 BOM 的 UTF-8。`CONTRIBUTING.md` 让用 `powershell -File`，也就是 Windows PowerShell 5.1，它按 ANSI/GBK 解码无 BOM 脚本，中文提示本来全是乱码。改存 UTF-8 BOM，换行保持 CRLF 以符合 `.gitattributes` 的 `*.ps1 text eol=crlf`。
3. 新增 `-CheckOnly`：只验解释器与依赖、不占端口，给新人自检和 CI 用。
4. 新增 `-Detached`：起完就返回并打印 PID。原脚本只能靠 `Read-Host` 按回车退出，后台或自动化场景会一直挂住。
5. 新增端口占用检测：目标端口已在监听就跳过并说明原因。原来会拉起一个立刻因 `Address already in use` 死掉的子进程，而且看不出来。
6. 就绪判定从「固定 sleep 猜」改成轮询 `/api/v1/health` 和 8090 的 TCP 连接，最多 8 秒，确认真的起来才算成功。
7. 缺 `websockets` 时直接给出 pip 命令并退出 1，不再等 `mock_ws` 崩了才回头猜原因。
8. 端口改为 `-ApiPort` / `-WsPort` 参数，默认仍是 8000 / 8090，行为对调用方不变。

## 已知风险与留待后续

- `README.md` 与 `CONTRIBUTING.md` 里的 `python -m venv .venv`、`pip install -r ...` 这两条，在 PATH 上 `python` 是商店占位符的机器上仍会失败。建议 T1 同步改成先说明「用真 Python 的绝对路径建 venv」，这属于文档改动，本次没动。
- `Makefile` 的 `dev` / `mock-api` / `mock-ws` 同样假定 PATH 有 `python`。macOS / Linux 与已激活 venv 的环境不受影响，Windows 上以 `tools/dev.ps1` 为准。
- 只在 Windows PowerShell 5.1 与 pwsh 下验证，未在 macOS / Linux 的 pwsh 上验证；`Get-NetTCPConnection` 仅 Windows 有。
- 本机 Python 是 3.13.5，高于 `pyproject.toml` 的 `target-version = "py312"`。ruff 与测试都过，但 W2 引入 Django 后建议固定到 3.12。
- 本文件与 `tools/dev.ps1` 需一起提 PR，交接人和工号请提交前改成真实值。
