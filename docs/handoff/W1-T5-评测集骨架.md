## 一句话说清它干什么

让「评测集本身对不对」进入 CI，把结构错误、剂量用例漏标、把真实患者信息写进仓库这三类问题在数据阶段就拦住。

## 数据流

`data/asr_cases.json`（20 条，四类各 5）与 `data/ocr_cases.json`（10 类单据）→ `test_eval_dataset.py` 读入并断言：id 唯一、类别齐全、剂量专项标在正确单据上、无身份证/手机号样式、音频目录未被误提交。样本音频与图片本身不进仓库（`.gitignore` 忽略 `*.wav` 与 `samples/`），所以结构校验与「跑评测」是两件事，前者现在可跑，后者等样本到位。

~~~mermaid
flowchart LR
  A[data/asr_cases.json 20 条] --> C[test_eval_dataset.py]
  B[data/ocr_cases.json 10 类] --> C
  C --> D{结构/类别/剂量标注}
  C --> E{PII 扫描}
  C --> F{样本目录未被提交}
  D --> G[CI: pytest backend/tests]
  E --> G
  F --> G
~~~

## 我改了什么（人工修改点）

1. **只校验结构、不校验样本存在**：录音按合规要求不进仓库，所以断言写成「音频文件应该都不存在」；一旦有人把 wav 提交进来，这条用例会红，正好当成 `.gitignore` 失效的报警器。
2. **剂量专项单独成判据**：`dose_check` 必须正好落在处方单、取药单、出院小结三类上，且这三类的 `required_fields` 必须含"剂量"。首版出院小结漏了该字段，就是被这条用例当场拦下的。
3. **加 PII 探测**：只做简版正则（18 位身份证、11 位手机号），覆盖最常见的误提交；不追求完整脱敏检测，那属于 W7 的安全走查。
4. **数据与用例分目录**：数据放 `data/`，校验放同层 `test_*.py`，后续接入真实评测脚本时不必搬家。
5. **AI 参与度：部分使用。** 初稿由 AI 生成；人工改动为上面 1–4 的取舍，以及首版剂量字段遗漏的修复。按 14 号 §6.1 A4，合并前仍需另一名成员做至少一处实质性修改。
