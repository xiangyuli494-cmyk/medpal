## 一句话说清它干什么

定下九张表和十一个状态节点，让三端读写同一份数据、说同一套字段名。

## 数据流

一次陪诊 = 一个 `Episode`。它挂 `timeline`（发生了什么）、`tasks`（要做什么）、`media`（材料）、`consents`（谁能看）。`Memory` 与 `AccessibilityProfile` 挂在 `User` 上跨单复用。状态跃迁由服务端写 `Episode.status`，同时往 `timeline` 追加一条，AI 调用另写 `audit_log`。

~~~mermaid
erDiagram
  User ||--o| AccessibilityProfile : has
  User ||--o{ Memory : owns
  User ||--o{ Episode : "elder of"
  Episode ||--o{ Timeline : records
  Episode ||--o{ Task : contains
  Episode ||--o{ Media : holds
  Episode ||--o{ Consent : grants
  Episode ||--o{ AuditLog : traces
~~~

## 我改了什么（人工修改点）

1. 实体数为 9 个。04 号裁决第 11 条要求补 `Media`：11 号只在 `Episode` 里写了 `media[]` 却没给字段，而 `Timeline` 与 `Task.evidence` 要引用它。补了 5 个字段（`id` / `episode_id` / `kind` / `confidence` / `human_checked`）。
2. `AuditLog` 补了 `episode_id` 与 `status`（裁决 12）。原表 6 字段里没有归属，审计查不到「这句是哪一单、哪个节点说的」，等于留痕白留。
3. 状态枚举命名统一。开工包的 `陪诊状态机.puml` 用 `PLAN` / `NAV` / `PAY_PICKUP` 三个缩写，与 19 号步骤表写的 `PLAN_EXAMS` / `NAVIGATE` / `PAY_AND_PICKUP` 不一致。以 19 号为准，puml 同步改，并登记在 §2.1。
4. 每个字段标了「最小可用」/「可延后」两档，并在 §5 汇总。这是 W1 冻结的核心：W2 只受理最小可用列，可延后字段 W4 前以 v0.2 追加，W4 后转技术债。
5. 补了 §6 八条不变量（I1–I8）。11 号只给字段不给约束，比如「撤销授权后家属端即时不可见」的判定依据是 `Consent.status` 与 `revoked_at`，不是 `Timeline.visibility` 的静态值——这条不写下来就会被实现成静态字段。
6. 补了 §7 差异登记 D1–D7，逐条说明本文件与 11 号 §4.3 的出入及原因，避免两个文件互相打脸。
7. 补了 §2.3 的 11 → 9 映射表与换算公式。02 号 §3.3 讲 11 节点、演示讲 9 步，中间没有换算规则就是各说各话。

## 已知风险与留待后续

- 无内嵌结构实体：`Episode.staff_contact` 只是一个工号字符串，不建关联表。
- `Media.confidence < 0.8 触发求证` 与 `Task.evidence` 的指向关系只是文字约定，没有形式化约束，W3 接真实识别时容易漂。
- 状态机 11 节点里 `FALLBACK` 是子状态而非主序列节点，`EpisodeStatus` 枚举该不该包含它还没定，W2 评审要拍。
- ER 图与 md 两处维护，改字段要同时改，没有自动校验。
