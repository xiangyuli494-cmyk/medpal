## 0 v0.2 变更：改用 `qwen-audio-3.1`，作废 qwen3 生成音频（2026-10-20）

**决策**：播报模型由 `qwen3-tts-flash` 切换为 **`qwen-audio-3.1-tts-flash`（音色 `longanhuan_v3.1`）**；当日上午用 qwen3 生成的全部音频（56 个文件，含两批 20 条与校准样本）**已作废并删除**。

**重新校准的结果**（同句 13 字，`qwen-audio-3.1-tts-flash`）：

| 档位 | 指令 | 时长 | 字/秒 | 相对基线 |
| --- | --- | --- | --- | --- |
| base | 无 | 2.72s | 4.8 | 1.00x |
| v1 | 语速比平时稍慢一点点 | 4.32s | 3.0 | 1.59x |
| **v2** | **请用比较缓慢的语速说话** | 4.00s | 3.2 | **1.47x** |
| v3 | 语速稍慢一点 | 4.96s | 2.6 | 1.82x |
| v4 | 语速放慢一点，但不要过慢 | 6.00s | 2.2 | 2.21x |

**关键结论：这个模型的语速是"跳档"的，0.86 倍速（理论 3.16s）在两档之间、无法精确命中。** 可达的只有 1.00x 与 ≥1.47x。因此改为按用途分两包：

| 包 | 指令 | 语速 | 用途 |
| --- | --- | --- | --- |
| `std_audio31` | 无 | 3.3–6.0 字/秒（均值 4.7） | 标准通道播报；数值上最接近 0.86（差 14%） |
| `elder_audio31` | 请用比较缓慢的语速说话 | 2.1–5.4 字/秒（均值 3.7） | 老人版播报；折合 0.68 倍速，比 0.86 更慢但更稳 |

两包各 20 条、24kHz 单声道原版 + 16kHz/16bit/单声道协议版，各耗 173 字 ≈ 0.0138 元，合成总耗时 12.7 秒。

> 下文 §1–§5 保留的是 qwen3 时代的实测证据（尤其 §2 证明数值 `rate` 参数无效），**这些结论对 audio-3.1 同样成立**，因此不再复述，仅作证据存档。

| 问题 | 结论 |
| --- | --- |
| 有没有数值化的语速参数？ | **没有可用实现**。`qwen3-tts-flash` 的 `parameters.rate` 不生效（见 §2） |

## 2 数值参数校准：`parameters.rate` 是无效的

同一条句、同一音色，只改 `rate` 值，重复测得：

| rate | 时长 | 字/秒 | 相对 1.0 |
| --- | --- | --- | --- |
| 1.0 | 3.44s | 3.8 | 1.00x |
| 0.95 | 3.20s | 4.1 | 0.93x |
| 0.90 | 3.20s | 4.1 | 0.93x |
| 0.86 | 3.12s | 4.2 | 0.91x |
| 0.80 | 3.20s | 4.1 | 0.93x |

**判读**：0.95→0.80 之间时长几乎不动（3.12–3.20s，差异在噪声内），只有 1.0 略长。若是线性生效，0.80 的时长应该是 3.44/0.80 = 4.30s，实测 3.20s。**结论：该参数未被模型采用，不能写进实现。**

> 这条要写进交接单：**不要按 11 号「TTS 语速 0.86」去实现一个 `rate=0.86` 参数，它不会生效。**

## 3 自然语言指令的档位（两个模型差别很大）

### 3.1 `qwen3-tts-flash`（推荐）

| 指令 | 时长 | 字/秒 | 相对基线 |
| --- | --- | --- | --- |
| 无 | 3.36–3.44s | 3.8 | 1.00x |
| 「请把语速放慢到大约平时的百分之八十五」 | 3.84s | 3.4 | **1.12x** |

目标 0.86 倍速（理论 4.00s）与实测 3.84s 相差 4%，**采用这条指令**。

### 3.2 `qwen-audio-3.1-tts-flash`（最快，但语速不受控）

| 指令 | 时长 | 字/秒 | 相对基线 |
| --- | --- | --- | --- |
| 无 | 2.72s | 4.8 | 1.00x |
| 「语速稍慢一点」 | 4.96s | 2.6 | **1.82x** |
| 「语速慢一些，像对老人说话那样」 | 4.88s | 2.7 | 1.79x |
| 「请用比较缓慢的语速说话」 | 3.76s | 3.5 | 1.38x |
| 「请用非常缓慢的语速说话」 | 7.52s | 1.7 | 2.76x |

**判读**：这个模型的指令是"跳档"的——连「稍慢一点」都会掉到 1.8 倍时长，无法稳定落在 0.86。它适合用默认语速（4.8 字/秒，对老人偏快），或接受跳到 2.6 字/秒。

## 4 批量合成 20 条后的速率分布（重要）

用 `qwen3-tts-flash` + Cherry + 85% 指令批量合成 20 条评测台词：

| 统计 | 值 |
| --- | --- |
| 成功 | 20 / 20 |
| 单条合成延迟 | 中位约 0.7 秒；平均 1.77 秒（含一条 21.6 秒的异常） |
| 合计耗时 | 35.3 秒 |
| 字符消耗 | 173 字 = **0.0138 元** |
| 语速区间 | **3.8 – 6.6 字/秒** |

**问题**：同一条指令下，语速并不一致——短句天然更快（`asr-09` 10 字 1.52s = 6.6 字/秒，`asr-16` 11 字 2.88s = 3.8 字/秒）。原因是短句缺少句中停顿，固定开销占比高。

**处置建议**（写进 W5 实现）：

1. 播报文本先按标点**切成 ≤ 20 字的短句**再逐句合成，避免长句一口气读完；
2. 单条延迟只有 0.7 秒左右，**逐句流式播放可行**，不必等整段合成；
3. 若某句实测快于 5 字/秒，对该句追加"更慢一点"的二级指令，而不是全局调档；
4. 不要用总平均语速做验收，**按句判定**——这与 ASR 评测"分类命中率"的逻辑一致。

## 5 可直接复制的请求参数

### 5.1 实时播报（推荐）

```json
POST https://dashscope.aliyuncs.com/api/v1/services/aigc/multimodal-generation/generation
{
  "model": "qwen3-tts-flash",
  "input": {
    "text": "请到二楼检验科，出电梯往左走",
    "voice": "Cherry",
    "language_type": "Chinese",
    "instruction": "请把语速放慢到大约平时的百分之八十五"
  }
}
```

### 5.2 预生成固定话术（入口播报 / 免责声明，可接受等待）

```json
POST https://dashscope.aliyuncs.com/api/v1/services/audio/tts/SpeechSynthesizer
{
  "model": "qwen-audio-3.1-tts-next",
  "input": {
    "text": "本设备仅提供就诊引导，不提供医学诊断。",
    "voice": "longanhuan_v3.1",
    "text_prompt": "请用温和、缓慢、清晰的语气播报，像医院志愿者对一位听力不太好的老人说话",
    "format": "wav",
    "sample_rate": 24000
  }
}
```

> `tts-next` 的 `text_prompt` 是**必填**，不传报 `text_prompt must not be empty`；控制台页面上那个"文本提示"框就是这个参数。注意它输出**立体声**，播报链路要做降混。
