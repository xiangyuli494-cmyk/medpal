| 项 | 内容 |
| --- | --- |
| 责任人 | T5 |
| 版本 | v0.1（2026-10-20） |
| 模型 | `qwen3.5-ocr`（实测通过，见 `docs/specs/ai-selection.md` §11） |
| 提示词正文 | `p-ocr-01-单据抽取.txt`、`p-ocr-02-剂量专项.txt`、`p-ocr-03-剂量复核.txt`（**单一来源，本文不复制正文**） |
| 依据 | 红线 R-2（不确定须标记不得推断）、00 号 §5（剂量错误数 = 0）、14 号 §6.2（提示词库） |

---

## 1 为什么拆成三支，而不是一支大提示词

| 提示词 | 什么时候用 | 为什么不能合并 |
| --- | --- | --- |
| P-OCR-01 单据抽取 | 常规识单：挂号单、检验单、缴费凭证等 | 通用抽取关注"有哪些字段"，字段多、易发散；剂量需要的是"抄准数值与单位"，约束完全不同 |
| P-OCR-02 剂量专项 | 处方单、取药单、出院小结 | **剂量是红线**。把剂量塞进通用提示词里，模型会顺手把"1片"规范化成"100mg"，这正是最危险的错误 |
| P-OCR-03 剂量复核 | 剂量专项之后第二次调用，或人工校对前 | 单次抽取错了自己发现不了；用"图 + 第一次结果"二次核对，能把不一致显式列出来 |

**成本**：P-OCR-02 + P-OCR-03 各调一次，单张约 0.0014 元（实测单张 0.000681 元）。相对剂量错误在医疗场景的代价，这个成本可以忽略。

---

## 2 三条实测约束（决定了提示词必须这样写）

| 约束 | 实测事实 | 提示词里的应对 |
| --- | --- | --- |
| **没有字段级置信度** | `qwen3.5-ocr` 返回体只有文本，`usage` 里也只有 token 数，**没有 per-field confidence** | 不确定性只能靠提示词强制输出 `?` 与 `uncertain_fields`；适配器层再把这些映射成低置信度（如 0.3），**不得伪造精确置信度** |
| 返回可能被代码块包裹 | 实测返回是 ```` ```json ... ``` ```` | 提示词明确"不要 markdown 代码块"，同时**适配器必须剥掉围栏**再 `json.loads`，不能只靠提示词 |
| 模型倾向"规范化" | 实测会把结构化字段整理成整齐 JSON | 提示词逐条禁止换算、改写、合并、补单位；但**最终仍要靠评测集验证**，不能假设约束一定生效 |

> 这三条同时说明：提示词是"降低错误概率"，不是"保证正确"。剂量字段的保证手段是 **P-OCR-03 复核 + 人工校对 + 评测集回归**，三层叠加。

## 3 字段对齐（提示词 ↔ 评测集 ↔ 数据结构）

提示词里的字段名必须与评测集、`OcrResult` 用同一套名字，否则评测无从比对：

| 提示词字段 | 评测集 `required_fields` | 适配器 `OcrResult.fields` |
| --- | --- | --- |
| 科室 / 医生 / 时间 | 挂号单、检查申请单等 | 同名字符串 |
| 项目 / 结果 / 参考区间 | 检验申请单、检验报告 | 同名字符串 |
| 药品名称 / 剂量 / 频次 / 疗程 / 数量 | 处方单、取药单 | 同名字符串 |
| 金额 / 总费用 / 医保支付 / 自付 | 缴费凭证、医保结算单 | 同名字符串 |
| 主诉 / 诊断 / 用药 / 部位 | 病历首页、出院小结、检查申请单 | 同名字符串 |

改字段名要同时改三处：提示词 `.txt`、`backend/tests/eval/data/ocr_cases.json`、`backend/adapters/base.py` 的 `OcrResult`。

## 4 怎么用（探针已支持 `--prompt-file`）

```powershell
# 通用抽取
python tools/probe/probe.py --preset dashscope --capability ocr --provider dashscope `
  --file tools\probe\samples\ocr\01_挂号单.jpg `
  --prompt-file docs\prompts\p-ocr-01-单据抽取.txt

# 剂量专项（处方单 / 取药单 / 出院小结）
python tools/probe/probe.py --preset dashscope --capability ocr --provider dashscope `
  --file tools\probe\samples\ocr\05_处方单.jpg `
  --prompt-file docs\prompts\p-ocr-02-剂量专项.txt
```

用 `--prompt-file` 而不是 `--text` 的原因：提示词含换行、花括号与中文标点，直接塞进命令行会被 PowerShell 吃掉引号（这个坑已经在实测中踩过两次）。

## 5 剂量专项的判定口径（与评测集联动）

对 `dose_check: true` 的三类单据（处方单、取药单、出院小结），逐条判定：

| 判定项 | 通过条件 |
| --- | --- |
| `dose_value` | 与原文数值完全一致（`0.5` 不能写成 `.5`，`1/2` 不能写成 `0.5`） |
| `dose_unit` | 与原文单位完全一致（`mg` 不能写成 `毫克`，缺失必须是 `""` 且登记到 `uncertain_fields`） |
| 多条用药 | 条数与原文一致，不能只输出第一条 |
| 模糊处理 | 图上看不清的必须是 `?` + `uncertain: true`，**猜出一个值即判为错误** |
| 错误计数 | 上述任一不符记 1 个错误；**错误总数必须为 0** 才可选用 |

## 6 失败处理与降级

| 情形 | 处理 |
| --- | --- |
| 返回不是合法 JSON | 适配器先剥 ```` ``` ```` 围栏再解析；仍失败则抛 `LegacyContractError` 同级的契约错误，转人工录入，**不得静默返回空结果** |
| `doc_type` 为 `unknown` | 转人工录入，并记录该图片（可能是拍摄质量问题） |
| `uncertain_fields` 非空 | 该单据进入人工校对队列，**不阻塞流程但不得自动完成** |
| 剂量出现 `?` | 强制人工校对，禁止自动播报（这是 R-2 的直接要求） |
