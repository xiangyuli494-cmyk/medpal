## 第 1 章 总则

本章规定组织设计依据、时间模型、交付物编号与阶段口径，作为后续各章的共同基准。

### 1.1 组织设计依据

项目组由 6 名在校学生组成，项目周期 24 周。组织设计遵循以下五项依据。

| 编号 | 依据 | 说明 |
| --- | --- | --- |
| ORG-1 | 单一责任人 | 每项交付物有且仅有一名责任人（Accountable）；责任人可分配工作，不得转移责任 |
| ORG-2 | 工作节奏隔离 | 领域逻辑（纯函数、可 100% 单元测试）与 AI 集成（外部依赖、供应商可替换）分设角色，避免外部能力变更波及领域层 |
| ORG-3 | 用户群体隔离 | 用户端面向记忆能力衰退的就医人群，工作台面向并行管理多名患者的陪诊师，两类产品不得由同一角色设计 |
| ORG-4 | 硬件独立性 | 硬件采购、烧录、结构、电源四项工作中任一项延期均会占用两周以上工期，不由其他角色兼任 |
| ORG-5 | 质量独立性 | 质量保证角色不承担业务功能开发；质量保证角色开始编写功能代码，测试独立性即失效 |

### 1.2 时间模型

全体成员为在校学生，学期内周一至周五以课业为主。项目开发工作仅安排在周末，具体安排如下。

| 时段 | 用途 | 时长 |
| --- | --- | --- |
| 周六 19:00 – 22:00 | 集成、联调、阶段性验收 | 3 小时 |
| 周日 19:00 – 22:00 | 开发、评审、周报 | 3 小时 |

有效投入按每人每周 4 – 8 小时核定（含周内零散时间），不作加班假设。

**排期原则**

1. 所有任务以周为最小排期单位，不设小于一周的任务项；
2. 每项任务须在一个周末内可完成，否则予以拆解；
3. 每个周末须产出可演示的增量，不允许连续两周无可演示成果；
4. 考试周（第 9 周、第 17 周）工作量按 50% 计，缓冲已在前序周预留。

### 1.5 权限层级定义

| 权限名称 | 定义 |
| --- | --- |
| 决定权 | 对指定事项作出最终结论的权限，结论须记录于 ADR 或 Issue |
| 提案权 | 就指定事项提出方案并提交评审的权限 |
| 否决权 | 对指定事项作出否决结论的权限，否决须以书面形式给出依据 |
| 建议权 | 提出意见但不具约束力的权限 |
| 豁免权 | 在书面记录技术债的前提下，有条件解除否决结论的权限 |

### 2.4 角色验收标准

| 代号 | 验收标准 |
| --- | --- |
| T1 | 领域层单元测试覆盖率 100%；会话协议自第 3 周冻结后只允许追加版本号，不允许修改既有字段语义；每 2 周至少产出 1 篇 ADR |
| T2 | 断电重启 30 秒内自动回到入口页；按绿键至页面响应小于 200ms；三种震动编码可被视障用户区分（5 人盲测）；续航不少于 4 小时；30 项硬件检查清单可执行并具备签名记录 |
| T3 | 老人版字号不小于 24pt 且可切换三档；家属端自收到推送至打开时间轴不超过 2 次点击；所有推送文案通过红线校验器（禁用词出现次数恒为 0）；用户可撤销任一授权，撤销后家属端即时不可见 |
| T4 | 同时管理 3 个 Episode 不发生混淆；低置信度字段全部进入人工校对界面，不得静默通过；每次人工修正留痕（操作人、时间、修正内容、原文）；双签流程含时间戳与存证 |
| T5 | 老人语速与方言样本 ASR 关键信息命中率不低于 80%（安静环境不低于 95%，自建 50 条测试集）；OCR 剂量字段错误数恒为 0；视障模式全程零点击可完成；听障模式旁白出声次数恒为 0；TTS 失败如实降级为字幕且不弹出错误框 |
| T6 | make test 单条命令执行全部测试且耗时小于 60 秒；CI 全绿为合并前提；新增代码覆盖率不低于 80%，领域层覆盖率 100%；禁用词出现次数为 0 与 OCR 剂量字段错误数为 0 作为 CI 硬门禁；每周六发布测试报告 |

### 2.5 角色制度约束

| 适用范围 | 约束条款 |
| --- | --- |
| T1 | T1 提交的代码同样须通过 T6 的合并门禁，无例外 |
| T2 | 设备端代码不得包含业务判断逻辑。设备端仅承担采集与渲染职责（架构决策记录 ADR-003） |
| T3 | 家属端不得提供实时定位功能 |
| T4 | 签字为 AI 禁入区。系统仅执行提醒应当签署与记录已经签署，不得代签 |
| T5 | ① 每项外部能力须先编写假实现（FakeASR、FailingASR），测试默认全部使用假实现；② 业务代码中不得出现任何供应商 SDK 的 import（含 dashscope、langchain_openai），该约束由 CI 的 grep 检查强制执行；③ 每周最多替换 1 个假适配器，替换后须执行完整回归测试并录制对比视频 |
| T6 | T6 不编写业务功能代码 |

### 2.6 T6 角色定位

T6 的职责定位由 ORG-5 导出，含以下三项。

| 定位 | 职责内容 |
| --- | --- |
| CI 的拥有者 | 拥有 CI/CD 流水线与质量门禁，对 main 分支的合并结论负责 |
| 验收的把关人 | 对发布验收结论负责，对质量门禁豁免申请行使审批权 |
| AI 生成代码的挑战者 | 构造边界用例、异常输入与并发场景，对 AI 生成代码的失败模式逐项验证并形成书面结论 |

T6 的专项工作内容为挑战 AI 生成代码，不包含常规功能可用性抽查。

## 第 3 章 职责矩阵（RACI）

本章按关键交付物列出执行、最终责任、咨询与知会四类角色，用于确定每项交付物的责任归属与评审范围。

### 3.1 RACI 定义

| 代号 | 名称 | 定义 |
| --- | --- | --- |
| R | 执行者（Responsible） | 承担实际工作 |
| A | 最终责任人（Accountable） | 对交付结果负最终责任；每项交付物有且仅有 1 名 A |
| C | 咨询者（Consulted） | 在交付前提供须被采纳的输入，双向沟通 |
| I | 知会者（Informed） | 接收结果通知，单向沟通 |

## 第 4 章 权限与制衡

本章规定各类决策的提议人、评审范围与裁决方式，并列出三项否决权的行使条件与解除条件。

### 4.1 决策权限表

| 决策类型 | 提议人 | 评审范围 | 裁决方式 | 记录方式 |
| --- | --- | --- | --- | --- |
| 产品范围与需求削减 | T1 | 全员评审 | T1 裁定；异议须在 24 小时内以 Issue 形式书面提出 | 需求规格更新 + Issue |
| 技术选型与架构 | T1 | 全员评审 | 异议方执行不超过 2 小时的验证实验，以实验数据裁定 | docs/adr/ |
| 交互与视觉 | T3 | T2、T5 执行可用性审查 | T2 或 T5 就可用性问题作出结论即为否决 | ADR 或 Issue，由 T1 记录 |
| 工作台操作流 | T4 | T3 提出建议 | T4 就并发可用性问题作出结论即为否决 | ADR 或 Issue，由 T1 记录 |
| AI 供应商与模型 | T5 | T6 执行评测 | 评测结果不达标即不予上线 | 评测报告 + ADR |
| 质量标准与合并 | T6 | 无 | T6 裁定；豁免须 T1 与 T3 同时同意，并将豁免理由记入 docs/tech-debt.md | 测试报告 + 技术债台账 |
| 接口契约变更 | T1 或受影响方 | T1 与受影响方 | 受影响方范围内不得存在未解决异议；通过后协议版本号递增 | ADR + 契约版本记录 |
| 紧急事项（里程碑前 48 小时） | T1 | 无 | T1 独断；仅允许实施使演示可运行的修改，技术债全量记入台账 | 技术债台账 |

### 4.2 否决权清单

| 编号 | 持有人 | 否决范围 | 行使条件 | 解除条件 | 记录要求 |
| --- | --- | --- | --- | --- | --- |
| V-01 | T2 与 T5（共同持有） | 无障碍达标性与交互可用性。含在视障或听障模式下不可用的功能，以及目标用户无法完成的交互设计 | 出具书面结论，说明目标用户无法完成的理由 | 修改设计后由 T2 与 T5 复核通过 | 结论记入 docs/accessibility/ 走查报告或对应 Issue |
| V-02 | T4 | 工作台并发可用性。含导致陪诊师同时管理 3 名患者时出现混淆或误操作的设计 | 出具书面结论，说明并发场景下的失败路径 | 修改工作台信息架构或操作流后由 T4 复核通过 | 结论记入对应 Issue 或 ADR |
| V-03 | T6 | 质量门禁。含缺少测试的 PR，对全体成员生效，含 T1 | 依据 CI 结果或缺失测试的事实作出结论 | 补充测试后由 CI 复验通过；豁免须 T1 与 T3 同时同意并记录豁免理由 | 结论记入测试周报的打回 PR 与质量门禁判定两节 |

### 4.3 制衡原则

1. 每项权力须有对应的书面记录方可生效，口头结论不构成决策；
2. 否决结论须同时给出依据与解除条件，不得只给出结论；
3. 质量结论存在争议时，以 CI 流水线结果为准；
4. 决策记录的载体为 Issue、ADR 或 docs/ 下的文档变更三者之一，群聊内容不构成决策记录。

本章规定项目统一术语。术语表存放于 docs/00-术语表.md 并持续维护，第 3 周定稿要求收录不少于 40 条术语；下表为角色与职责范围内的核心术语。

### 8.1 术语定义

| 术语 | 代码名 | 规范定义 | 禁止叫法 |
| --- | --- | --- | --- |
| 陪诊单 | Episode | 一次完整的陪诊服务过程，为全系统主干实体 | 订单、任务、case |
| 会话 | Session | 设备与用户之间的一次连续对话 | 对话、chat |
| 留痕 | Timeline / Media | 过程记录，含时间、照片、录音、凭证 | 日志（日志专指 AuditLog） |
| 复述校验 | Recall Check | 要求用户复述一遍以确认听懂 | 确认、核对 |
| 兜底 | Fallback | 任一步骤阻塞时的降级路径 | 异常处理 |
| 升级 | Escalation | 由 AI 移交给人的动作 | 报警 |
| 陪诊师 | Companion | 真人陪诊服务人员 | 护士、护工 |
| 红线校验器 | Guard | 拦截越界话术的规则组件 | 过滤器 |
| 证据链 | Evidence Chain | 一句话从事实到出口的五段生成记录 | 日志 |

### 8.2 术语使用纪律

1. 面向用户的文案、代码标识符与文档表述均须与术语表一致；
2. 违反术语表的 PR 予以打回；
3. 新增术语须在第 3 周定稿前提交；定稿后新增术语须通过变更控制流程；
4. 同一概念不得使用多个名称，代码标识符不得使用本表禁止叫法列中的表述。
