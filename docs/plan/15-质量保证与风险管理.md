## 1. 总则

本章规定本文件的编制目的、依据文件、质量职责与权力划分、时间口径，以及二十四周质量内容的压缩处置。

### 1.1 编制目的

1. 将 12 号文件的技术规范转化为可判定的质量目标，明确阈值、验证方式与责任人；
2. 明确质量保证活动、质量门禁、缺陷管理与回归策略的执行方式；
3. 明确风险登记、监控频率、概率重估与预先约定的延期应对规则；
4. 明确技术债台账与豁免流程，使质量门禁的例外情况可追溯；
5. 明确需求、技术、接口与进度四类变更的申请与审批流程，并给出八周工期的范围冻结机制；
6. 明确 M1 至 M4 里程碑的验收标准与验收流程。

配置管理相关要求中，分支保护、提交规范与基线文件管理见 12 号文件 2.1 节分支策略与 2.3 节 Python 规范；基线文件的变更记录见本文件第 7 章。

### 1.4 时间口径

1. 全体成员为在校学生，课余时间不固定且各不相同，本项目不设统一工作时段；每人每周有效投入按 4 – 8 小时核定，具体投入时段由个人自行安排；
2. 工时弹性，交付节奏固定：每周一 20:00 周计划会下达任务包，每周日 24:00 为任务包交付截止，次周一计划会前完成异步交付确认；全部质量活动按周任务包排布，不绑定固定时段；
3. 每个里程碑周不新增任务，预留当周工时的 50% 用于缺陷清扫，该缓冲随当周任务包一并预留；
4. 所有质量活动以周为最小单位排期，不设小于一周的活动项；
5. 八周周期内不预设考试周。如遇临时考试或课程冲突，当周工作量按 50% – 70% 排并允许顺延一项任务，不得压缩里程碑，亦不得以考试为由放宽红线指标。

### 1.5 二十四周质量内容的压缩处置

八周工期下，原二十四个月的十一轮双周活动、二十四周逐周活动与五次里程碑验收不具备整体平移的条件。本节对每一项原质量活动给出处置，处置类型限于五类。压缩不得降低第 2.1 节的阈值，亦不得删除第 4 章与第 8 章的检查项。

#### 1.5.1 处置类型

| 处置 | 定义 | 判定依据 |
| --- | --- | --- |
| 保留 | 内容与频次不变，仅压缩单周工时 | 属红线指标的验证手段，或属里程碑验收的强制输入 |
| 提前 | 原周次前移，内容不变 | 后置会使缺陷在 W8 前无修复窗口 |
| 合并 | 与相邻周期内的同类活动并入同一次执行 | 两项活动使用同一批用户、同一批素材或同一次评审会 |
| 降级为条件交付 | 移入 C1 – C6，仅在触发条件成立时执行 | 验证对象本身已成为条件交付项 |
| 删除 | 本周期内不执行，且不进入条件交付清单 | 与基线第 3.3 节的明确不做项重合，或对象已不在交付范围 |

### 2.3 质量目标未达成的处理

1. 硬门槛未达标时，CI 判定失败，PR 不得合并；
2. 红线指标出现违规时，T6 立即停止相关模块的合并，并启动专项修复；
3. 里程碑验收时未达标项须在验收报告中逐条列示处理方式与责任人，处理方式限于降级、延期与取消三类；
4. 因豁免或降级产生的质量缺口须登记入技术债台账，见第 6 章；
5. 八周周期内不得以「测试数不足由后续补齐」为由通过里程碑；测试数与评测集条数为累计硬门槛，未达标即判定该里程碑不通过。

## 4. 质量控制

本章规定质量门禁、缺陷分级标准、缺陷处理流程、回归策略与测试数据合规约束。

### 4.1 质量门禁

| 时机 | 门禁内容 | 判定人 |
| --- | --- | --- |
| 提交前，本地 | pre-commit 执行格式化、lint 与快速单元测试 | 提交人 |
| PR 创建 | CI 全绿；新增代码覆盖率 ≥ 80%；领域层覆盖率 100% | T6 |
| PR 合并 | 至少 1 人 approve；T6 确认具备验证证据；无未建 Issue 的 TODO 遗留；随代码提交对应文档 | T6 |
| 每周任务包交付 | 交付截止前在真实网络下执行完整流程并提交证据；发布测试报告 R2 | T6 |
| 每个里程碑 | 人工探索测试；P0 与 P1 缺陷清零；报告归档 | T6 |
| 发布与演示前 | 冒烟清单、硬件检查清单（C3 或 C4 触发时）、回滚方案确认 | T6、T2 |

补充规则：

1. 没有测试的 PR 不允许合并，该规则对全体成员生效，包括 T1；
2. 评审人须留下至少一条实质性评论，无实质评论的 PR 由 T6 打回；
3. 质量门禁的豁免按第 6.3 节执行；
4. AI 评测集的定时执行由 CI 任务承担，不占用成员工时；八周周期内执行频率为每周一次并保留全量报告。

### 4.2 缺陷分级标准

| 等级 | 定义 | 典型示例 | 响应时限 | 闭环时限 | 判定人 |
| --- | --- | --- | --- | --- | --- |
| P0 | 阻塞主流程、造成数据错误或合规风险、导致演示无法进行 | 剂量字段识别错误；仓库出现真实患者数据；设备端无法启动 | 发现后 24 小时内确认并指派 | 下一个交付截止点（周日 24:00）前修复；里程碑验收前必须清零 | T6 |
| P1 | 主流程可用但关键功能受损，无绕行手段 | 状态机节点无法跃迁；推送全部失败 | 48 小时内确认并指派 | 当周任务包周期内（周日 24:00 前）修复；里程碑验收前清零 | T6 |

说明：

1. 响应时限指缺陷的确认、分级与指派，可在线上完成，不受统一时段限制；闭环时限以周任务包的交付截止（周日 24:00）计算；
2. 等级由 T6 判定，对分级存在异议时以 T6 结论为准；
3. 缺陷等级调整须在缺陷台账中记录调整原因；
4. 八周周期内 P2 的闭环时限由两周压缩为一周，原因为 M2 之后不再接受新增功能，缺陷须在下一个里程碑前清空。

### 4.3 缺陷处理流程

| 步骤 | 内容 | 责任人 | 时限 |
| --- | --- | --- | --- |
| 1 登记 | 发现缺陷后当日登记，字段见附录 A | 发现人 | 当日 |

## 6. 技术债管理

### 6.1 技术债台账字段

| 字段 | 说明 |

1. 每次质量门禁豁免、紧急变更、里程碑验收与范围冻结转出，均须产生技术债记录；

## 7. 变更控制

本章规定需求变更、技术变更、接口变更与进度变更的申请与审批流程，并给出八周工期的范围冻结机制。

### 7.1 变更类型与审批矩阵

| 变更类型 | 申请方式 | 审批人 | 记录方式 | 时限 |
| --- | --- | --- | --- | --- |
| 需求增删 | 提交 Issue，标注 `change-request` | T1 | 需求规格更新与等量置换记录 | 周计划会 |
| 技术方案变更 | 提交 ADR 草案 | 全员评审 | `docs/adr/` | 每两周不少于 1 篇，八周内不少于 4 篇 |
| 接口契约变更 | 提交 Issue 并附影响面分析 | T1 与受影响方 | 协议版本号递增 | 当周 |
| 进度延期 | 周计划会提出 | T1 | 计划基线更新 | 周计划会 |
| 质量门禁豁免 | 书面申请 | T1 与 T3 同时同意 | 技术债台账 | 合并前 |
| 范围冻结后的功能变更 | 提交 Issue 并附等量置换方案 | T1 裁决，T6 核对置换量 | 范围冻结清单与技术债台账 | 当周 |
| 紧急变更，里程碑前 48 小时 | T1 直接决策 | T1 | 技术债台账全量登记 | 即时 |

决策依据：项目范围变更由 T1 裁决，异议须在 24 小时内以 Issue 形式书面提出；技术选型与架构变更由异议方执行不超过 2 小时的验证实验，以实验数据裁决，结论写入 ADR。八周周期内，变更的评估、裁决与登记须在同一周任务包周期内闭环，最迟不晚于当周周日 24:00 交付截止。

### 7.2 变更申请流程

| 步骤 | 内容 | 责任人 | 时限 |
| --- | --- | --- | --- |
| 1 提出 | 以 Issue 形式提交，写明变更内容、理由、影响面、等量置换方案与替代方案 | 申请人 | 变更发生前 |
| 2 影响面分析 | 评估对接口契约、测试用例、排期与里程碑的影响 | 申请人、相关责任人 | 提出后 1 个工作日内 |
| 3 评审 | 按第 7.1 节确定审批人；技术方案变更须全员评审 | 审批人 | 当周任务包周期内 |
| 4 批准与记录 | 批准后更新对应基线文件与范围冻结清单，并同步相关责任人 | 审批人 | 批准当日 |
| 5 验证 | 变更实施后执行第 4.4 节规定的回归范围 | 责任人、T6 | 实施当周 |
| 6 复核 | 在下一周期的风险登记表更新中复核变更影响 | T1 | 两周内 |

### 7.3 变更控制原则

1. 接口契约在 W2 冻结后，仅允许追加次版本号，不得修改既有字段语义；
2. 新增功能前须明确被替换掉的等量工作，不允许只做加法；
3. 里程碑前 48 小时内仅接受缺陷修复类变更；
4. 质量门禁的豁免不属于变更控制的常规通道，按第 6.3 节执行；
5. W4 范围冻结后，功能边界的变更一律按第 7.5 节执行，不得以「小改动」为由绕过冻结。

### 7.4 变更记录

| 变更类型 | 记录位置 |
| --- | --- |
| 需求增删 | 需求规格说明书与范围冻结清单 |
| 技术方案 | `docs/adr/` |
| 接口契约 | `docs/api/ws-protocol.md` 与 `docs/api/openapi.yaml` 的版本号 |
| 进度延期 | 计划基线 |
| 质量门禁豁免与紧急变更 | `docs/tech-debt.md` |
| 范围冻结后的功能变更 | 范围冻结清单、技术债台账与里程碑验收报告 |

每周测试周报与成员周报须列示当周变更；里程碑验收报告须列示本阶段全部变更及其影响。

### 7.5 八周工期的范围冻结机制

本节为八周版新增。范围冻结是压缩工期下控制范围失控的唯一强制手段，与 RK-11 对应。

#### 7.5.1 冻结时点与对象

| 项 | 规定 |
| --- | --- |
| 冻结时点 | W4 结束，以 M2 验收通过并签发范围冻结清单为准 |
| 冻结对象 | 必须交付 12 项的功能边界；会话协议主版本；领域模型最小可用字段集；三端的页面与视图清单 |
| 冻结方式 | 由 T1 编制 `docs/scope-freeze-W4.md`，逐条列示范围内功能、条件交付项与明确不做项，全员签认 |
| 冻结后的受理范围 | 仅受理缺陷修复、红线合规整改与演示脚本调整三类 |
| 冻结解除 | M4 验收通过后自动解除；提前解除须由 T1 书面裁定并记入技术债台账 |

#### 7.5.2 变更须换等量工作

| 规则 | 内容 |
| --- | --- |
| 等量定义 | 以人时计量，新增工作的人时不得大于被换出工作的人时；换出项须在冻结清单中真实存在 |
| 置换时点 | 置换须在当周任务包周期内可完成；跨周才能完成的置换不予受理 |
| 置换审批 | 由 T1 裁决，T6 核对人时并确认回归范围覆盖换出项与换入项 |
| 置换记录 | 换出项标注为转入条件交付或转入技术债，换入项登记 Issue 并关联冻结清单条目 |
| 禁止做法 | 以「先做后补」方式并行推进未置换的新增需求；以压缩测试为代价换取功能增量 |

#### 7.5.3 超出部分的自动转入

| 情形 | 处置 |
| --- | --- |
| 新增需求有等量置换 | 换入项进入本周期，换出项按第 7.5.2 节登记 |
| 新增需求无可置换项 | 不得进入本周期，自动转入条件交付清单 |
| 条件交付清单已满或无匹配项 | 登记入技术债台账并标注为不做，不进入本周期，在项目总结报告中列示 |
| 任务实际耗时超出计划且无法在当周吸收 | 超出部分按周计量，从 C 类与设备端非核心视图中等量削减，不得从测试与文档中削减 |
| 里程碑验收未达标项 | 按第 5.3 节处置，转入项标明为降级、延期或取消三类之一 |

#### 7.5.4 冻结记录与复核

1. 范围冻结清单随 PR 仓库管理，每次置换须在同一周内更新清单并在周报中列示；
2. T6 在每次里程碑验收的数据核对中核对冻结清单与代码仓库的差异，差异项须逐条说明；
3. 冻结清单的差异条数在 W8 验收时作为范围控制结论的量化依据；
4. 冻结机制本身不得被变更：W4 之后不得修改冻结时点、等量置换规则与自动转入规则，修改此类规则须由 T1 书面裁定并同步更新本文件版本号；
5. 冻结清单的差异说明宜以表格逐条列示，列明差异项、处置方式与责任人，供 W8 验收引用。

## 8. 验收管理

本章规定 M1 至 M4 里程碑的验收标准、验收流程、验收结论处理与交付物核对。

### 8.1 里程碑验收标准

| 里程碑 | 阶段 | 周次 | 验收标准 |
| --- | --- | --- | --- |
| M1 | P1 | W2 | 三端骨架可启动；CI 全绿；测试数 ≥ 40；领域层纯函数单测覆盖率 100%；会话协议 v0.1 与领域模型最小字段集冻结确认 |
| M2 | P2 | W4 | 9 状态节点全通；测试数 ≥ 120；E2E ≥ 8 条；P0 与 P1 缺陷清零；范围冻结清单签发 |

### 8.2 验收流程

| 步骤 | 时间 | 责任人 | 产出 |

### 8.3 验收结论与未达标项处理

1. 验收结论须逐条对应第 8.1 节的验收标准，并附证据链接；
2. 存在未达标项时，须在验收报告未达标项一节列明未达标原因、处理方式与责任人，处理方式限于降级、延期与取消三类；
3. 验收不通过时，由 T1 在下一周计划会重新分解任务，并按第 5.3 节处理；
4. 未达标项产生的技术债须登记入台账，见第 6 章；
5. 八周周期内任一里程碑连续两次验收未通过，由 T1 直接执行第 5.3 节的削减方案，不再重新分解。
