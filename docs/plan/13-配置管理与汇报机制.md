## 2 工具链选型

本章规定协作与工程工具的选定方案、否决方案及其理由。

### 2.1 选型表

| 用途 | 选定工具 | 否决方案 | 否决理由 |
| --- | --- | --- | --- |
| 代码托管、PR、Issue、看板 | GitHub，含 Repository、Projects、Actions | Gitee；GitLab 自建 | Gitee 的 CI 能力不足；GitLab 自建维护成本高；GitHub 与 CI 一体，Projects 看板免费，学生私有仓库免费 |
| 即时沟通 | 微信群或 QQ 群用于通知；GitHub Discussions 用于技术讨论 | 仅使用单一聊天群 | 群消息不构成留痕；技术结论须落 Issue 或 ADR，否则三日后再无依据 |
| 文档协作 | Markdown 入仓库 docs/ | 飞书、腾讯文档 | 在线文档与代码脱节；仓库内文档可随 PR 一并评审 |
| 会议 | 腾讯会议，重要会议录屏 | 无 | 录屏构成留痕，是会议可追溯的唯一凭据 |
| 任务看板 | GitHub Projects，四列 Backlog、This Week、In Review、Done | Trello | 与 Issue 脱节；Projects 与 Issue、PR 自动联动 |
| 设计稿 | Figma 免费版 | 无 | 第 4 周后按需启用 |
| 接口文档 | drf-spectacular 生成 OpenAPI 与 Swagger UI | 手写 Word 文档 | 契约即代码，CI 可校验 |
| 监控与日志 | Sentry 免费版 | 无 | 不在本期范围（条件项，W8 后评估） |
| 时间管理 | 团队共享日历 | 无 | 例会须进入日历，否则必然出现缺席 |

### 2.2 留痕纪律

口头或群内讨论形成的结论，须于当日落为 Issue、ADR、docs/ 文档改动三者之一；否则视为未形成决定。

| 结论类型 | 留痕载体 | 责任人 | 时限 |
| --- | --- | --- | --- |
| 任务与缺陷 | Issue | 提出人 | 当日 |
| 技术决策 | ADR，存放于 `docs/adr/` | 决策提议人 | 当日 |
| 规格、接口与流程变更 | `docs/` 文档改动，与代码同一 PR | 配置项责任人 | 当日 |

### 2.3 会议留痕

| 项目 | 规定 |
| --- | --- |
| 录屏范围 | 里程碑评审会、双周评审会及一切涉及决策的会议 |
| 录屏归档 | 归档至素材库，命名含周次与日期 |
| 结论转化 | 会议结论须在当日转化为 Issue、ADR 或文档改动，不得仅保留录屏 |

## 3 配置管理

本章规定仓库结构、分支模型、版本号规则、接口契约版本管理、文档与代码同步要求、配置项责任人及变更控制。

### 3.1 仓库结构

采用单仓库结构。六人团队跨端改动频繁，多仓库同步不产生收益。

```
medpal/
├── .github/workflows/ci.yml
├── docs/
│   ├── 00-术语表.md
│   ├── specs/             # 功能规格。先写规格，再写测试，最后写实现
│   ├── adr/               # 架构决策记录
│   ├── api/openapi.yaml   # 前后端并行开发的契约基础
│   ├── api/ws-protocol.md # 会话协议
│   ├── accessibility/     # 无障碍验收标准
│   └── test/              # 测试计划与周报
├── backend/
│   ├── domain/            # 纯逻辑，零外部依赖，单元测试覆盖率 100%
│   ├── adapters/          # ASR / TTS / OCR / LLM / RAG / 推送 的接口与实现
│   ├── apps/              # Django 应用
│   └── tests/
├── device/                # Kiosk 前端、设备服务与启动脚本
├── frontend/
│   ├── user-app/          # 用户端 uni-app
│   ├── family/            # 家属端 H5
│   └── companion-console/ # 陪诊师工作台
├── firmware/              # ESP32-C3 按键固件
├── hardware/              # 3D 模型、接线图、BOM、测试协议
└── tools/                 # 脚本、数据、素材
```

| 目录 | 内容 | 责任人 |
| --- | --- | --- |
| `backend/domain/` | 陪诊状态机、检查规划引擎、话术模板引擎、红线校验器、置信度策略、记忆库接口 | T1 |
| `backend/adapters/` | 七类能力的接口与实现，每类含真实实现与假实现 | T5 |
| `backend/apps/` | Django 应用、接口层、会话编排、实时通道 | T1 |
| `backend/tests/` | L1 – L5 测试代码与 `eval/` 评测集 | T5 与 T6 |
| `device/` | Kiosk 页面、设备服务、启动脚本 | T2 |
| `frontend/user-app/` | 用户端 App 与小程序，uni-app 工程 | T3 |
| `frontend/family/` | 家属端 H5 | T3 |
| `frontend/companion-console/` | 陪诊师工作台与运营后台 | T4 |
| `firmware/` | ESP32-C3 按键固件 | T2 |
| `hardware/` | 3D 模型、接线图、BOM、测试协议与测试记录 | T2 |
| `docs/` | 术语表、规格、ADR、接口契约、无障碍标准、测试文档 | T1 |
| `tools/` | 脚本、脱敏数据与素材 | T6 |
| `.github/workflows/` | CI 流水线配置 | T6 |

### 3.2 分支模型

| 分支 | 命名格式 | 用途 | 生命周期 | 合并要求 |
| --- | --- | --- | --- | --- |
| main | main | 基线分支，任何时刻可运行且 CI 全绿 | 永久 | 仅接受 PR；至少 1 人 approve；CI 通过 |
| 功能分支 | feat/F-{功能号}-{简述} | 功能开发 | ≤ 1 周 | 见 12-开发规范与测试规范 §2.1 |
| 缺陷分支 | fix/issue-{编号}-{简述} | 缺陷修复 | ≤ 1 周 | 同上 |
| 测试分支 | test/T-{编号}-{简述} | 测试补充 | ≤ 1 周 | 同上 |
| 文档分支 | docs/{简述} | 文档修订 | ≤ 1 周 | 同上 |

| 纪律 | 规定 |
| --- | --- |
| 直接推送 | 禁止向 main 直接推送；禁止强制推送 |
| 同步 | 每周至少执行一次 `git pull --rebase origin main`，交付截止前必须已合入当周 main |
| 超期处理 | 分支存活超过 3 天须拆小，或先合并可用版本并以 feature flag 关闭未完成功能 |
| 提交规范 | 提交信息须符合 Conventional Commits 与 scope 白名单，见 12-开发规范与测试规范 §2.2 |

### 3.3 版本号规则

| 配置项 | 版本标识 | 递增规则 | 审批人 |
| --- | --- | --- | --- |
| 接口契约 | `docs/api/openapi.yaml`，路径前缀 `/api/v1/` | 新增可选字段或新增端点递增 MINOR；文字澄清递增 PATCH；破坏性变更递增 MAJOR | T1 与受影响方 |
| 会话协议 | `docs/api/ws-protocol.md`，第 1 周冻结 v0.1 | 追加字段递增 MINOR；字段语义变更递增 MAJOR 并走变更控制 | T1 |
| 领域模型 | `docs/specs/domain-model.md`，第 1 周冻结 v0.1 | 同会话协议 | T1 |
| 应用发布版本 | 里程碑冻结版本，对应 M1 – M4 | 每个里程碑验收通过后打一次基线标签，标签含里程碑编号与验收日期 | T1 |
| 固件 | `firmware/`，自 v0 开发板验证版本起递增 | 每次烧录版本变更须递增并记录 | T2 |
| 文档 | 本文件与 00、10、11、12、14、15、16 号文件，当前基线 v3.0 八周版 | 评审通过的实质性修订递增 MINOR；文字性修订递增 PATCH | 编制人 |
| 架构决策记录 | ADR-001 至 ADR-014，单向递增 | 不得修改已发布 ADR 的结论；变更以新 ADR 记录并标注被取代关系 | T1 |

### 3.4 接口契约版本管理

| 项目 | 规定 |
| --- | --- |
| 契约载体 | `docs/api/openapi.yaml` 与 `docs/api/ws-protocol.md` |
| 冻结时点 | W1 冻结会话协议 v0.1 与领域模型 v0.1（最小可用字段集）；W4 范围冻结后为基线 |
| 允许的变更 | 新增可选字段、新增端点、澄清性文字修订 |
| 禁止的变更 | 修改既有字段语义、类型与必填性；删除既有字段 |
| 破坏性变更 | 须提交 Issue 与影响面分析，由 T1 与受影响方审批，MAJOR 递增，旧版本至少保留一个阶段 |
| 校验方式 | CI 执行 schemathesis 契约校验；前后端接口不一致即判定失败 |
| 验证手段 | 会话协议须存在可由 `websocat` 直接打通的 mock 服务 |

### 3.5 文档与代码同步要求

| 要求 | 规定 |
| --- | --- |
| 同仓管理 | 文档与代码同仓库，文档随代码走 |
| 同 PR 变更 | 接口与规格变更须与对应代码在同一 PR 内提交；由评审人核对 |
| 规格先行 | 先写 spec，再写测试，最后实现；无 spec 与测试的代码不得进入 main |
| 术语一致 | 违反 `docs/00-术语表.md` 的 PR 打回 |
| 归档 | 测试报告、验收报告、走查报告与素材须归档至 `docs/test/` 与素材库 |

### 4.1 汇报体系

| --- | --- | --- | --- | --- | --- | --- |

### 4.2 汇报纪律

| 序号 | 纪律 |
| --- | --- |
| 1 | 未按时提交周报者，由项目经理在周计划会通报 |
| 2 | 周报中"本周完成"栏须附验证证据，含截图、录屏、测试输出或接口返回 |
| 3 | 未提供验证证据的工作项不计入完成率 |
| 4 | 测试周报中的红线结论，即禁用词数与剂量错误数，由 T6 独立判定，不受其他成员影响 |
| 5 | 汇报模板以 14-项目实施计划.md 附录 A 至附录 D 为唯一版本，不得另行维护副本 |

### 4.3 专项测试用例基线

T6 每周须构造不少于 5 条边界与异常用例，并在测试周报中列示。下表为已验证的基线用例。

| 序号 | 构造输入 | 预期结果 |
| --- | --- | --- |
| 1 | ASR 返回空字符串 | 走求证流程，不崩溃 |
| 2 | 同一张单据连续上传 3 次 | 幂等，不重复记账 |
| 3 | 剂量字段 0.5g 与 5g 混淆 | 标为不确定，不做纠错 |
| 4 | 短信网关返回 500 | 失败可见化并进入重试队列 |
| 5 | 候诊中途断网 3 分钟 | 本地缓存并在恢复后重放 |

## 8 全程可控机制与风险应对

本章规定全程可控的落实机制、延期应对规则与风险登记表的管理要求。

### 8.1 五项控制机制

| 序号 | 机制 | 具体做法 | 缺失后果 |
| --- | --- | --- | --- |
| 1 | 契约先行 | 第 1 周冻结会话协议、领域模型与端口约定；第 3 周冻结后仅追加版本号 | 各端相互等待，前端等后端，硬件等软件 |

| 3 | 证据链文化 | 每个 PR 须填写验证证据；每人于双周评审会以 5 分钟陈述实证；AI 产出登记造册 | 进度无法核实 |
