## 1. 评估范围与结论

### 1.1 评估对象

| 编号 | 原型名称 | 载体 | 提供人 |
| --- | --- | --- | --- |
| PA | 医学知识图谱模块 | Python 包（`tests/kg`） | 成员 A |
| PB | 陪诊助手·长辈版 | 单文件 Web 应用 | 成员 B |
| PC | 院内便携式语音陪诊终端·交互原型 | 单文件 Web 应用 | 成员 C |
| PD | 小暖陪诊 v2 / v3 / index | 单文件 Web 应用及配套方案文档 | 成员 D |

### 1.2 评估结论

四份原型并非同一产品的迭代版本，而是分别覆盖产品不同层面的独立成果，具体分工如下：

| 原型 | 覆盖层面 | 独有内容 |
| --- | --- | --- |
| PA | 推理内核 | 唯一具备真实数据规模、自动化测试集与参数标定记录的模块 |
| PB | 交互合规 | 唯一将 AI 输出边界以代码形式强制约束的原型 |
| PC | 系统集成 | 唯一将演示过程本身作为工程问题处理的原型 |
| PD | 产品定义 | 唯一完成用户分层、交互契约与产品形态定义的原型 |

### 1.3 融合原则

1. 不以页面拼接方式合并，而以**内核抽取**方式融合；
2. 融合后的每一功能模块须可追溯至具体来源原型；
3. 融合版本须补充四份原型共同缺失的能力（见第 5 章）。

## 2. 原型 PA · 医学知识图谱模块

### 2.1 模块说明

实现路径为「自由文本 → 图谱节点 → 图遍历加权投票 → 科室推荐」，不依赖 Web 框架，采用 pymysql 直连 MySQL。提供两级节点选择（规则层、LLM 层）。

### 2.2 可复用成果

| 编号 | 成果 | 说明 |
| --- | --- | --- |
| PA-1 | 数据规模 | 节点 20,465 条、边 131,363 条、别名 10,895 条，可直接作为生产数据资产 |
| PA-2 | 测试集 | 分 5 个文件共 125 个用例（配置 36、工具层 38、数据完整性 28、图数据健康度 23） |
| PA-3 | 调优记录 | 疾病起点不做症状扩散。实测症状扩散导致「腰腿痛」由 1 票污染为 191 票，将错误科室推至首位，据此确立「医疗场景精度优先于召回」原则 |
| PA-4 | 儿科过滤策略 | 实测「上不来气」时「儿科内科」102 票高于「呼吸内科」100 票。处理方式为引入儿科科室识别，并规定年龄未知时同样排除儿科科室；判定不得仅匹配「儿」字，须排除「试管婴儿」「胎儿」「产前」「孕」等干扰项 |
| PA-5 | 置信度口径 | 明确置信度为相对票数占比而非准确率，不得与需求文件中的 0.85 阈值混用 |

### 2.3 缺陷与处置

| 缺陷 | 处置 |
| --- | --- |
| 无界面，终端用户不可见 | 融合版本增补「语音分诊」页面及知识图谱推理面板 |
| 查询辅助模块自述非生产代码，测试与生产代码未分层 | 融合时收入 `backend/adapters/kg/` 统一管理 |

### 2.4 在最终演示版本中的落点

设备端「语音分诊」页面（含红旗预警覆盖）；系统面板「知识图谱推理」（数据规模、遍历路径、加权投票、儿科过滤依据）。

## 3. 原型 PB · 陪诊助手·长辈版

### 3.1 原型说明

单文件移动端应用，含 7 个视图与 1 个通话层，覆盖「看不清、不会用、说不清、记不住医嘱、求助无门」五类使用障碍。

### 3.2 可复用机制

| 编号 | 机制 | 实现要点 |
| --- | --- | --- |
| PB-1 | 字号全局缩放 | 采用 `:root` 设计令牌与 `calc(var(--body)*var(--scale))` 联动，字号三档仅需修改单一变量；附带对比度实测值 11.4:1 与 4.6:1 |
| PB-2 | 医嘱可追溯卡片 | 结构化抽取结果与原文并列展示，推断字段标注「系统推断」徽章，卡片末尾固定展示原始文本 |
| PB-3 | 送达状态如实回执 | 离线状态下返回 `notify:{sent:false, reason:...}`，界面文案改为「未能自动通知家人」，并全屏提供 `tel:` 拨号入口 |
| PB-4 | 语音三级降级 | 云 TTS → 浏览器 speechSynthesis → 纯字幕；任一级失败均不弹出错误提示 |
| PB-5 | 语音播放时序 | 播报结束后再执行页面跳转，避免播报被跳转中断 |
| PB-6 | 双模数据探测 | 依据 `location.protocol` 与后端探测结果切换数据源，同一渲染逻辑支持演示模式与联机模式 |
| PB-7 | 纯函数意图解析与测试出口 | 意图评分采用最长关键词优先策略；导出 `window.__xnTest` 测试入口 |

### 3.3 需求可追溯性

该原型未自行编订需求编号，而是引用《面向老年用户的陪诊系统功能补充调研报告》的章节坐标（第 5 章正文 ≥18pt、按钮 ≥48dp；第 5.2 节多模态反馈与首次语音引导），需求具备可追溯来源。

### 3.4 缺陷与处置

| 缺陷 | 处置 |
| --- | --- |
| 挂号流程未闭环，选择科室后仅提示「演示模式下不再继续」 | 融合版本补全至二次确认与取号结果页 |
| `innerHTML` 全量重建导致焦点与滚动位置丢失；事件重复绑定依赖手工维护 | 融合版本改为单向数据流，控制面板仅修改状态对象 |
| 同名函数被整体重新赋值覆盖，难以测试；`chat` 意图映射至不存在视图并静默返回主页 | 融合版本取消函数覆盖写法，未定义视图须显式报错 |
| 医嘱仅取首条，多条被忽略；「全部念一遍」采用固定 6 秒间隔，与真实语速不符 | 融合版本按条渲染并采用播报完成事件驱动 |

### 3.5 在最终演示版本中的落点

全站字号缩放令牌；「我的用药医嘱」页面（医生原话卡片）；送达状态如实回执机制（求助与推送失败场景）；语音三级降级链。

## 4. 原型 PC · 院内便携式语音陪诊终端·交互原型

### 4.1 原型说明

三栏演示台结构（演示控制台、仿硬件终端、外部系统），覆盖建档、点位讲解、语音分诊、二次确认挂号、院内导航、医生回传、家属短信、求助工单、归还清空完整链路。

### 4.2 可复用机制

| 编号 | 机制 | 实现要点 |
| --- | --- | --- |
| PC-1 | 命令总线架构 | 以 `data-cmd` 属性配合 `runCommand` 统一分派，参数以冒号分隔。将屏幕控件、控制台、语音三类入口收敛为单一命令流，已作为融合版本的事件架构基础 |
| PC-2 | 点位触发上下文 | 8 个点位各具编号；关键流程中仅插播不换屏；进入采血、放射区域自动触发安抚话术 |
| PC-3 | 情绪陪伴引擎 | 11 场景话术库；去重策略避免重复播报；暖色样式与功能区隔；可独立开关；90 秒无操作自动触发空闲关怀 |
| PC-4 | 情绪优先仲裁 | 语音处理首步执行情绪识别，命中情绪表达时直接返回，避免「我一个人来的，心里有点怕」被误判为症状或导航指令 |
| PC-5 | 红旗预警 | 覆盖心血管与神经两类指征，追问回答为「有」时改推急诊科并强制触发升级路径 |
| PC-6 | 失败可见化与双端闭环 | 推送失败生成失败气泡、「重试发送」按钮与重试倒计时；求助工单含点位、患者、年龄、联系人信息，服务台受理后反向播报 |
| PC-7 | 演示保险丝 | 脚本被拦截时显示 `#noScriptWarn` 说明；`window.onerror` 将异常写入横幅；无中文语音包时如实降级为字幕；提供键盘快捷键 |

### 4.3 需求编号

原型已建立需求编号体系：FR-01（电源与身份、医生工作站档案保存）、FR-02（点位触发）、FR-05（一键求助）、FR-06（家属推送）。合规标签「仅院内租借使用·离院收回」「模拟测试数据·不录入真实人脸或身份证」「分诊仅作就诊参考，不能替代医生诊断」在结果页与语音播报中重复出现。

### 4.4 缺陷与处置

| 缺陷 | 处置 |
| --- | --- |
| 无持久化，刷新后回到演示起点 | 融合版本启用审计日志与指标状态留存 |
| 演示控制设施与业务逻辑耦合（`powerOn()` 内直接修改控制台控件） | 融合版本改为一）控制台仅修改状态，二）渲染层单向读取 |
| 语音解析为约 15 条单层正则顺序判定；肯定与否定应答采用顺序互斥兜底，存在相互干扰风险 | 融合版本改为意图评分与显式优先级 |
| 挂号序号写死；科室匹配未采用最长优先策略 | 融合版本改为动态生成与最长优先匹配 |
| 无障碍支持仅有黄白对比切换，无字号档位 | 融合版本引入 PB-1 的字号缩放令牌 |

### 4.5 在最终演示版本中的落点

事件总线架构、演示控制台、情绪陪伴条、红旗预警引擎、故障注入面板、演示保险丝。

## 5. 原型 PD · 小暖陪诊 v2 / v3 / index

### 5.1 原型说明

包含入口分流、三类用户交互契约、虚拟形象、医保讲解、无障碍适配，以及硬件方案、家属端方案、点位讲解方案三份配套文档。

### 5.2 可复用成果

| 编号 | 成果 | 说明 |
| --- | --- | --- |
| PD-1 | 入口分流与交互契约 | 老年人（大字触控与记忆辅助）、视力障碍（全程语音、零点击）、听力障碍（文字优先与替我说）三类契约；入口页提供长按 2 秒进入语音模式的盲人可达路径 |
| PD-2 | 步数化导航 | 视力障碍通道采用「行走步数 + 触觉地标」描述方式，不使用左右方位；物品统一置于左手侧以适配盲杖使用习惯 |
| PD-3 | 替我说 | 听力障碍通道提供文字转语音输出，输出目标为医生而非用户本人；该通道下系统旁白不出声 |
| PD-4 | 虚拟形象 | 纯内联 SVG 实现，含五种表情状态，无外部图片依赖；形象设定明确不穿白大褂、不持听诊器、不出现医疗器械 |
| PD-5 | 医保费用讲解 | 采用总额、医保支付、自付三栏结构，配合甲类、乙类、丙类逐项拆解；明确不由系统决定用药，并附费用免责声明 |
| PD-6 | 设计规范文档 | 「人情味六层能力」模型（记得住、主动、说明白、兜底、有边界、给尊严），每层附带可验收指标与反例 |
| PD-7 | 话术模板 | 四段式结构：承接情绪、提供信息、给出确定性、保留退路 |
| PD-8 | 置信度交互策略 | 大于 95% 直接展示；80% – 95% 高亮提示；低于 80% 不给出结论 |
| PD-9 | 检查规划约束清单 | 空腹、憋尿、排尿冲突、固定预约、楼层动线、用户状态六类约束；明确采用规则引擎而非优化算法 |
| PD-10 | 配套方案文档 | 硬件方案（含 BOM 与风险清单）、家属端方案（论证微信形态）、设备端逐屏信息架构（11 节点 × 界面要素） |

### 5.3 缺陷与处置

| 缺陷 | 处置 |
| --- | --- |
| 三个文件各维护一套页面与话术数据，逻辑重复 | 融合版本统一为单一数据层 |
| 深链参数通过 hash 解析，通道间状态不共享，「一内核三通道」未在原型中体现 | 融合版本实现状态共享：切换通道仅更换渲染层，会话状态不重置 |
| 全部 AI 能力为预置文本，无生成过程记录 | 融合版本新增证据链面板 |

### 5.4 在最终演示版本中的落点

通道切换、视力障碍与听力障碍两条完整通道、虚拟形象、医保页面、9 节点状态机、全流程话术。

## 6. 融合版本新增能力

融合版本（`medpal-demo/v4.html`）在四份原型基础上新增以下三项能力，用以覆盖共同缺失项。

| 编号 | 新增能力 | 说明 |
| --- | --- | --- |
| N1 | 证据链面板 | 面向用户的每一条输出，可展开为「事实 → 模板 → LLM 润色 → 红线校验 → 输出」五段记录。用于验证 AI 输出的可控性 |
| N2 | 故障注入 | 支持注入五类故障：ASR 低置信度（0.41）、断网、短信网关异常、剂量模糊（0.5g / 5g）、越界话术。用于验证系统降级、求证与升级路径，四份原型均仅覆盖正常路径 |
| N3 | 设备端逐屏界面 | 含 11 节点逐屏、触摸控件映射、兜底子状态机、点位讲解。四份原型均只覆盖局部，`demo/device-prototype.html` 是唯一完整实现，本模块是产品本体的直接证据 |

此外，融合版本实现状态共享：多个视角共用同一会话状态对象，切换视角仅更换渲染层；设备端状态机与家属端时间轴指向同一 Episode 实体。

## 7. 四份原型共同缺失项与应对

| 共同缺失项 | 应对措施 |
| --- | --- |
| 仅覆盖正常路径，未演示异常处理 | 新增故障注入面板（5 类故障） |
| AI 输出不可追溯，无法证明可控性 | 新增证据链面板与审计日志 |
| 无业务数据持久化 | 审计日志与指标留存于状态对象；正式系统写入 AuditLog 表 |
| `innerHTML` 全量重建，状态与视图易脱节 | 采用单向数据流 |
| 无自动化测试出口 | 内核函数（规划打分、图谱投票、红线校验、模板渲染）均实现为纯函数，可由 CI 直接调用 |

### 7.1 相关纪律

融合版本中的全部纯函数，须在正式代码仓库中具备对应的 pytest 单元测试。演示版本用于演示，测试用于保证实现一致性。
