## 3. 项目目标与里程碑

### 3.1 项目目标

1. 建成以陪诊状态机为内核、覆盖四类用户通道的陪诊服务系统；
2. 交付一台可通电运行的院内便携终端；
3. 形成完整工程资产：需求规格、架构决策记录、接口文档、自动化测试体系、测试报告；
4. 完成不少于 10 位目标用户的可用性测试并形成量化评估报告。

### 3.2 里程碑

| 阶段 | 周次 | 里程碑 | 验收标准 |
| --- | --- | --- | --- |
| P0 | W1 – W3 | M1 | 三端骨架可启动；CI 全绿；测试数 ≥ 60；领域层覆盖率 100% |
| P1 | W4 – W8 | M2 | 设备端走完 9 个状态节点；测试数 ≥ 200；E2E ≥ 15 条 |
| P2 | W9 – W14 | M3 | 真语音对话可用；识单剂量字段零错误；AI 评测集 ≥ 200 条 |
| P3 | W15 – W19 | M4 | 真机开机至语音应答完整链路；无障碍问题闭环率 ≥ 80% |
| P4 | W20 – W24 | M5 | 真机演示无人工干预；测试数 ≥ 400；文档包齐备 |

## 5. 项目管理纪律

### 5.1 五条开发纪律

1. 先编写规格说明，再编写测试，最后交由 AI 生成实现；缺少规格与测试的代码不得合并至 main 分支。
2. 单次 AI 生成任务规模不超过 300 行、不超过 1 个模块，超出须拆解。
3. AI 生成的代码须由另一名成员进行实质性修改后合并；无法修改视为未理解，予以退回。
4. T6 拥有合并否决权；缺少测试的合并请求一律退回，对项目经理同等适用。
5. 每名成员均为单点故障风险；第 4、12、20 周各执行一次互备演练。

### 5.2 三条强制性约束

| 编号 | 约束 |
| --- | --- |
| R-1 | 医学相关表述须以医生原话为来源，不得表述为系统判断 |
| R-2 | 识别不确定时须标记并求证，不得推断，剂量字段尤须遵守 |
| R-3 | 重要医疗材料须电子化留存并完成交接双签 |

### 5.3 变更控制

| 变更类型 | 审批人 | 记录方式 |
| --- | --- | --- |
| 需求增删 | T1 | 需求规格更新 |
| 技术方案变更 | 全员评审 | `docs/adr/` |
| 接口契约变更 | T1 及受影响方 | 协议版本号递增 |
| 进度延期 | T1 | 计划基线更新 |
| 质量门禁豁免 | T1 与 T3 同时同意 | 技术债台账 |

接口契约在第 3 周冻结后，只允许追加版本号，不允许修改既有字段语义。

## 6. 全程可控机制

| 编号 | 机制 | 要点 |
| --- | --- | --- |
| 1 | 契约先行 | 第 1 周冻结会话协议与领域模型；第 3 周后只允许追加版本号 |
| 2 | 测试约束 | 领域层纯函数 100% 单元测试；AI 输出以评测集与阈值管控；T6 持合并否决权 |
| 3 | 证据链要求 | 每个合并请求须填写验证证据；未提供证据的工作项不计入完成率 |
| 4 | 定期接管 | 每两周白板讲解一个模块；每两月结对换手；第 4、12、20 周互备演练 |
| 5 | 降级预案 | 三条延期应对规则预先约定，见 [15-质量保证与风险管理](15-质量保证与风险管理.md) |
