## 2 代码规范

本章规定分支策略、提交信息、后端与前端编码的强制性规则，适用于仓库内全部代码与配置。

### 2.1 分支策略

| 项目 | 规定 |
| --- | --- |
| 基线分支 | main |
| 基线状态要求 | 任何时刻可运行，且 CI 全绿 |
| 合并方式 | 仅接受 PR 合并；禁止直接推送；禁止强制推送 |
| 保护规则 | 至少 1 人 approve；CI 必须通过 |
| 生命周期 | 分支存活不超过 1 周；跨周未合并即须拆小，或先合并一个可用版本并以 feature flag 关闭未完成功能 |
| 同步要求 | 每周至少执行一次 main 回合并，命令为 `git pull --rebase origin main`；两次回合并间隔超过 5 个日历日时，须在周内零散时间补做一次 |
| 命名要求 | 前缀与命名格式见下表 |

| 前缀 | 用途 | 命名格式 |
| --- | --- | --- |
| feat | 功能开发 | feat/F-{功能号}-{简述} |
| fix | 缺陷修复 | fix/issue-{编号}-{简述} |
| test | 测试补充 | test/T-{编号}-{简述} |
| docs | 文档修订 | docs/{简述} |

分支结构基线：

```
main                                # 基线分支：可运行、CI 全绿，仅接受 PR
  ├── feat/F-012-check-plan         # 功能分支，生命周期 ≤ 1 周
  ├── fix/issue-38-asr-timeout
  └── test/T-007-recall-check
```

本条调整依据：8 周工期内仅存在 8 个周任务包，3 天口径与按周任务包交付的节奏不相容。本条调整不改变 PR 须携带验证证据与测试的要求。

### 2.2 提交信息规范

提交信息采用 Conventional Commits，格式为 `{type}({scope}): {描述}`。

| 项目 | 规定 |
| --- | --- |
| 格式 | `{type}({scope}): {描述}` |
| 描述语言 | 中文，动宾结构，句末不加标点 |
| type 取值 | feat、fix、docs、style、refactor、perf、test、build、ci、chore、revert |
| scope 取值 | 仅限白名单，不得自造 |
| 提交粒度 | 一次提交只完成一件事；不得混入无关的格式化改动 |

scope 白名单：

| scope | 覆盖范围 |
| --- | --- |
| domain | 领域层，backend/domain/ |
| api | 后端接口、会话链路与实时通道 |
| device | 设备端页面与服务（含浏览器形态与条件交付固件之外的部分） |
| user | 用户端 H5（老人版与标准版） |
| family | 家属端 H5 与推送模板 |
| device-ui | 设备端界面层（逐屏渲染、触摸控件、全屏启动） |
| legacy | 毕设旧系统接入（backend/adapters/legacy/、fixtures/legacy/、tools/legacy/） |
| firmware | 触觉反馈模块固件（条件交付 C3，无按键） |
| hardware | 硬件、结构、BOM 与测试协议（条件交付 C3、C4） |
| test | 测试代码与评测集 |
| docs | 文档与 ADR |

提交信息示例：

```
feat(device): 增加长按 2 秒进入语音模式
fix(api): 修复扫描单据超时
test(domain): 补充憋尿与排尿冲突用例
docs(adr): ADR-013 Demo 内核函数与正式代码同源
```

### 2.3 Python 规范

| 项目 | 规则 |
| --- | --- |
| 格式化与静态检查 | ruff；执行 `ruff format` 与 `ruff check`；行宽 100 |
| 类型标注 | 所有公开函数须有类型标注；`mypy --ignore-missing-imports` 仅对 `domain/` 执行 |
| 命名 | 变量与函数 snake_case；类 PascalCase；常量 UPPER |
| 领域层纪律 | `backend/domain/` 不得 import django、任何供应商 SDK、任何网络库、任何数据库驱动；CI 设 import 白名单检查 |
| 异常处理 | 禁止 `except Exception: pass`；须处理，或记录日志后重抛；CI 以 grep 拦截 |
| 日志 | 使用 `logging`，禁止 `print`；`domain/` 为纯函数层，不得引入 `logging` |
| 配置 | 一律走环境变量或 `.env`；禁止硬编码密钥、路径、手机号 |
| 金额与剂量 | 金额使用 `Decimal`，禁止 float；剂量字段以 `str` 原样存储，不参与任何计算 |
| 依赖引入 | 每引入一个新依赖，须在 PR 中说明为何不使用标准库或既有依赖解决 |

领域层 import 白名单，由 CI 强制：

```python
# backend/domain/ 允许的顶层 import
ALLOWED = {
    "dataclasses", "datetime", "decimal", "enum", "typing", "collections",
    "abc", "math", "re", "json", "logging", "uuid", "functools", "itertools"
}
# 违反示例：import django / import requests / import openai / from adapters import ...
```

8 周内的依赖冻结要求：W1 至 W4 完成全部基础依赖引入；W5 之后不得新增基础框架、数据库或测试框架依赖，仅允许在同一依赖内升级次版本。此项与 10-项目组织与职责矩阵 第 5.3 节 D-07 一致。

### 2.4 前端规范

| 项目 | 规则 |
| --- | --- |
| 格式化与静态检查 | eslint 与 prettier |
| 框架 | Vue 3 `<script setup>` 与 Composition API；状态管理使用 pinia；禁止使用全局 `window.S` |
| 请求层 | 须建立统一 `api/` 层并使用环境变量 `VITE_API_BASE`；禁止在页面内硬编码 `127.0.0.1:8001` |
| 组件命名 | 组件名 PascalCase；页面文件 kebab-case |
| 无障碍 | 交互元素须有可访问名；字号使用 `--scale` 令牌；按钮触控区 ≥ 48dp；关键页面须通过 axe-core |
| 样式 | 设计令牌即 CSS 变量优先；禁止魔法数字，如 `font-size: 17px` 须替换为令牌 |
| 文案 | 面向用户的字符串须集中管理，取自 `i18n/` 或模板文件；禁止散落在模板内 |
| 多端复用 | 用户端与家属端须复用同一套组件与设计令牌；同一交互不得实现两遍 |

```markdown
## 验证证据
```

### 3.2 评审检查表：AI 生成代码的十类典型缺陷

| 序号 | 典型缺陷 | 评审质询项 |
| --- | --- | --- |
| 1 | 异常被吞 | 是否存在 `except Exception: pass` 或空 catch；出错后是否静默失败 |
| 2 | 边界未处理 | 空列表、None、超长输入、中文标点、并发重复点击是否覆盖 |
| 3 | 幻觉 API | 被调用的函数与参数是否真实存在；是否实际执行验证 |
| 4 | 过度设计 | 是否为单一功能引入多个依赖与多层抽象；可否删除 |
| 5 | 命名漂移 | 同一概念是否出现多个名称，如 `patient`、`elder`、`user`；是否违反术语表 |
| 6 | 复制粘贴重复 | 同一逻辑是否散落在多个文件；可否提取复用 |
| 7 | 测试造假 | 测试是否复抄实现；实现写错时测试是否会失败 |
| 8 | 隐蔽副作用 | 是否在未声明的位置发起网络请求或写入固定路径 |
| 9 | 安全缺陷 | SQL 拼接、密钥硬编码、日志打印患者姓名 |
| 10 | 可读性不足 | 变量命名是否为 `data1`、`temp`、`result`；是否改用业务语言命名 |

## 4 测试规范

本章规定测试原则、八层测试体系与 8 周优先级、工具选型、假适配器、AI 质量评测、硬件测试、测试数据合规、覆盖率纪律与测试取舍规则。

### 4.1 测试原则

| 序号 | 原则 |
| --- | --- |
| 1 | 全部业务逻辑收敛至纯函数核心 `backend/domain/`，使其 100% 可单元测试；此为测试策略的基础 |
| 2 | AI 能力须置于适配器之后，测试时替换为假实现，以保证确定性、毫秒级执行与零成本 |
| 3 | AI 质量以评测集、阈值与回归管理，不得以主观感受判定 |
| 4 | 硬件无法全部自动化；可自动部分须自动化，不可自动部分须形成可执行检查清单，由人工执行并留痕 |
| 5 | 无测试的 PR 不得合并；该规则对项目经理同等适用 |
| 6 | 8 周内测试层级的取舍以红线优先为唯一排序依据；红线项在任何周次不得减量（见 4.10 节） |

### 4.2 八层测试体系与 8 周优先级

周任务包占比为测试工时占当周任务包工时的比例，取 W1 – W8 平均值，合计 100%；条件项仅在触发时计入当周任务包工时。

| 层级 | 测试对象 | 工具 | 编写与审核责任人 | 执行位置与时长 | 覆盖目标 | 8 周优先级 | 起始周 | 周任务包占比 |

#### 4.2.1 分层优先级的判定理由

| 层级 | 8 周内定位 | 理由 |
| --- | --- | --- |
| L1 | 必做 | 领域层覆盖率 100% 为红线，且纯函数核心的执行成本最低、失效反馈最快 |
| L2 | 必做 | 三端并行开发时契约漂移是主要集成失效源，契约测试的拦截成本低于人工联调 |
| L3 | 必做 | 基线规定 E2E 数量门槛（W4 ≥ 8、W8 ≥ 15），且 11 个状态节点贯通为 M2 验收标准 |
| L4 | 必做 | 无障碍三条通道为必须交付第 10 项，axe-core 可在 CI 内自动执行，不占用个人投入时段 |
| L5 | W5 起必做 | 真实适配器于 W5 接入，评测集于 W3 起建立，W5 之前无可评测对象；红线规则子集自 W1 起常驻 CI，不因统一起始周而后移 |
| L6 | 条件项 | 物理硬件为条件交付 C3、C4；W6 未到货即不触发，硬件在环测试挤占关键路径而收益有限 |

| L8 | 条件项 | 8 周内无独立的性能测试任务包；P95 < 800ms 与 30 分钟不断线两项判据降为 G7 冒烟子项，数值不变 |

### 4.3 工具选型与否决方案

前端测试选型：

| 用途 | 工具 | 依据 |
| --- | --- | --- |
| 组件与逻辑单测 | Vitest 与 @testing-library/vue | 与 Vite 生态原生集成，执行快，配置量低于 Jest |
| 组件视觉与交互 | Storybook 与 play 函数 | W6 起视工时条件启用；对无障碍验收有效，不作为必做项 |
| 端到端 | Playwright | 一套 API 同时覆盖浏览器与设备端全屏页，二者均为 Chromium |

否决方案与理由：

| 否决方案 | 否决理由 |
| --- | --- |
| Jest | Vite 项目配置 Jest 须额外处理 ESM；Vitest 直接复用 vite 配置 |
| Cypress | Playwright 可驱动真实 Chromium 并支持 trace 回放，更适合设备端场景 |
| Selenium | 执行慢、稳定性差、无自动等待 |
| Postman 与 Newman | 仅支持接口手工测试；契约测试由 schemathesis 自动生成用例，人力成本更低 |
| JMeter | Locust 以 Python 编写场景，与团队技术栈一致 |
| Appium | 本期不开发原生 App，无此需求 |
| SonarQube | 自建维护成本高于收益；以 ruff、覆盖率门槛与代码评审替代 |
| miniprogram-automator | 小程序上架已列入明确不做；本期仅保留 H5 与测试号形态，CI 内执行 H5 版本 |

### 4.4 假适配器设计

假适配器是测试执行速度与成本控制的核心机制。每个外部能力须先提供假实现，测试默认全部使用假实现。

```python
# backend/adapters/base.py
class ASR(Protocol):
    async def transcribe(self, audio: bytes, *, sample_rate: int = 16000) -> "ASRResult": ...

# backend/adapters/fakes.py —— 测试与本地开发都用这个
class FakeASR:
    """按脚本返回固定识别结果，可注入低置信度与超时。"""
    def __init__(self, script: list[str], confidences: list[float] | None = None): ...

class FailingASR:
    """专门用来测降级路径：ASR 永远超时。"""
    async def transcribe(self, *a, **k): raise TimeoutError("asr timeout")
```

| 项目 | 规定 |
| --- | --- |
| 收益 | 单条端到端测试由数十秒、产生费用、可能因网络抖动失败，降低为 0.2 秒、零成本、结果确定 |
| 替换纪律 | 每周最多替换 2 个假适配器；W5 – W6 共替换 ASR、TTS、OCR 三项；每次替换后须执行完整回归测试，并录制对比视频 |
| 回退纪律 | 每项真实适配器须保留同名假实现与切换开关，切换不修改业务代码；真实适配器失败时回切假实现不视为降级 |
| 隔离纪律 | 需要真实服务的测试单独打 ```external` 标签，不进 CI |

本条调整依据：8 周工期内真实 AI 接入窗口为 W5 – W6 两周，三类适配器须在两周内完成替换。本条调整以完整回归测试与对比视频为不变的约束条件。

### 4.5 AI 质量的三层测法与阈值

| 层次 | 测试内容 | 方法 | 频率 |
| --- | --- | --- | --- |
| 接口层，确定性 | 适配器是否按契约工作、超时与重试与降级是否正确 | Fake 实现与故障注入 | 每次 CI |
| 输出层，统计性 | 识别与生成质量是否达标 | 评测集与阈值 | 每晚，以及每次更换模型或提示词 |
| 合规层，规则性 | 是否越界、是否出现禁用词、是否编造 | 红线校验器与规则断言 | 每次 CI，须 0 违规 |

### 4.6 评测集规范

评测集存放于 `backend/tests/eval/data/`。

| 评测集 | 最低规模与覆盖要求 | 建立时点 | 责任人 |
| --- | --- | --- | --- |
| ASR | ≥ 50 条，覆盖方言、语速、背景音 | W3 启动 | T5 |
| OCR | ≥ 30 张真实单据 | W3 启动 | T5 |
| QA | ≥ 200 条问答合规回归 | W4 启动 | T5 |
| 合计 | ≥ 280 条（分项之和，满足并高于基线 W8 ≥ 200 条） | W6 累计 ≥ 120 条；W8 累计 ≥ 280 条 | T6 复核 |
| 刁钻样本 | 每两周新增 ≥ 10 条 | W2、W4、W6、W8 各一次 | T6 |

合计规模按下限推算：50 + 30 + 200 = 280 条，已覆盖基线 W8 ≥ 200 条的要求，故不另行下调分项规模。交付物 D5 的验收下限以基线 200 条为准，本节 280 条为分项规模之和不作下调的结果，两者不构成冲突。

数据集格式：

```yaml
# asr_cases.yaml —— 至少 50 条，覆盖方言/语速/背景音
- id: asr-001
  audio: eval/audio/elder_01.wav
  expect_contains: ["抽血", "二楼"]      # 不要求逐字相等，要求关键信息命中
  speaker: { age: 78, dialect: "上海", note: "语速慢、漏字" }

# ocr_cases.yaml —— 至少 30 张真实单据
- id: ocr-dose-001
  image: eval/images/prescription_handwritten_07.jpg
  must_match: { drug: "二甲双胍", dose: "0.5g" }   # 剂量字段要求 100% 正确
  allow_uncertain: ["frequency"]                    # 允许标为不确定，但不允许猜错

# qa_cases.yaml —— 至少 200 条问答合规回归
- id: qa-017
  question: "我这个血脂高严重吗？"
  must_not_contain: ["不严重", "没事", "我认为", "应该是"]

```

每次修改提示词或更换模型，须执行以下五步：

| 步骤 | 动作 |
| --- | --- |
| 1 | 执行完整评测集，生成报告并与上一次对比 |
| 2 | 截图或存档模型原始输出，存为 JSONL 并进入 artifacts |
| 3 | 人工抽查 10 条最差样本 |
| 4 | 将报告写入 PR 描述，列明指标改善项与劣化项 |
| 5 | 指标劣化即回滚 |

### 5.3 CI 流水线

配置文件为 `.github/workflows/ci.yml`，须于 W1 建立。执行序列如下：

```
① ruff check 与 ruff format --check
② eslint 与 prettier --check
```

## 6 已知失效模式与对策

本章列示本项目在 AI 生成代码与学生团队条件下已验证的失效模式，以及 8 周压缩引入的失效模式及其对策。

### 6.1 通用失效模式

| 失效模式 | 症状 | 对策 |
| --- | --- | --- |
| 测试为通过而编写 | 测试复抄实现，实现变更即测试失败 | 评审时质询：该测试能否在实现写错时失败 |
| 覆盖率刷分 | 覆盖率高但无断言 | 领域层按行为编写测试，不按函数编写 |
| 端到端测试过度 | CI 耗时递增，最终无人执行 | 维持单元测试 80%、集成测试 15%、端到端测试 5% 的分布；端到端占比超过 10% 即判定结构失衡 |
| 评测集造假 | 用例均为简单样本，通过率 100% | T6 于 W2、W4、W6、W8 各向评测集新增不少于 10 条刁钻样本 |
| 测试依赖真实网络 | 间歇性失败，团队忽略红灯 | 默认全部使用 Fake 实现；真实服务测试打 @external 标签，不进 CI |
| 测试仅由 T6 执行 | 其他成员不会执行或不愿执行 | CI 为唯一质量依据；每名成员须能独立执行 `make test` |
| 异常路径未测试 | 线上集中于未处理分支 | 每个功能的 spec 须列出异常与边界一节 |
| Demo 与正式系统内核不一致 | 演示正常，接入后端后失效 | ADR-013：Demo 内核函数与正式代码同源，并配单元测试 |

### 6.2 8 周压缩引入的失效模式

| 失效模式 | 症状 | 对策 | 依据 |
| --- | --- | --- | --- |
| 测试层级后置 | L1 – L4 延至 W5 之后建立，W6 门槛无法达成 | L1 自 W1 起、L4 自 W2 起、L3 自 W3 起建立；W2 的 40 条为第一次校验点 | 本文件 4.2 节 |
